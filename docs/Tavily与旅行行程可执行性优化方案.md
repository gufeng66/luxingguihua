# Tavily 与旅行行程可执行性优化方案

版本：1.1

日期：2026-10-26

状态：修订后的实施方案；本次只修改文档，功能尚未实现。

## 1. 目标与交付边界

本次改动解决一个闭环：景点事实进入约束，约束改变排程，地图和最终行程表使用同一份结果。

第一项交付是修复现有行程数据被后处理覆盖的问题；这一项不依赖 Tavily。随后在编排层接入搜索和真实交通耗时，再补确认卡与修订持久化。

| 已确定的规则 | 方案 |
| --- | --- |
| 搜索位置 | 编排层固定查询；地图子智能体只提交高德候选 |
| 搜索预算 | 最多 6 次 HTTP 尝试，单次最多 8 秒，共同窗口 30 秒；重试计入总数 |
| 硬约束依据 | 已核对域名、摘要中的原文子串、可确定的适用日期，以及可明确解析的规则 |
| 信息不明 | 行程照出，相关开放或交通条件标为未核实 |
| 每日安排 | 默认 09:00—18:00；景点数量服从时间预算与必去要求 |
| 市内交通 | 默认公共交通＋短距离步行，尊重明确自驾偏好 |
| 输入扩展 | 只增加 must_visit、avoid、transport_mode |
| 产物 | 候选、约束、按天行程三块数据；地图与表格均由行程生成 |
| 持久化 | 使用现有快照，增加 schema_version；SQLite 表结构保持现状 |

“可执行”只表示在已获取规则、交通结果和明确假设下未发现冲突。没有官方依据、交通耗时未知，或用户原话中的时刻与预约尚未被结构化验证时，只能称为候选方案。

## 2. 需要修复的现有行为

| 位置 | 现有行为 | 必须改变的结果 |
| --- | --- | --- |
| planner/pipeline.py | HTML 存在时调用 reorder_existing_map() | 停止无条件重排，以服务端规范行程为准 |
| planner/map_fallback.py | 从 HTML 取出名称、坐标、备注，丢失分天和交通段 | 新流程直接消费结构化候选，不从 HTML 恢复规划事实 |
| planner/route_plan.py | 每天最多 4 个点，超量时按离住宿远近裁剪 | 必去项不被静默裁掉；按时间可行性删减非必去项 |
| planner/route_plan.py | 所有交通段生成 walking | 保留实际选用的公交、步行或自驾模式 |
| planner/map_agent.py | 每天要求 3～4 个景点；坐标不足时允许使用参考坐标 | 取消固定数量和猜坐标要求，只接受高德返回的地点 |
| planner/summary.py | 行程表由模型自由成文 | 成文后用程序表格替换“行程表”整章正文 |

只把搜索结果附加到 map_context，仍然会被上述重排覆盖，不能算完成接入。

## 3. 调用流程与职责

```text
用户输入 / 已确认槽位
  → 原有规则路由、主智能体调度
  → 地图子智能体：使用现有高德 skill，返回候选 JSON
  → 编排层：校验候选，固定模板查询 Tavily
  → 编排层：保存摘要，按有限规则提取并验证约束
  → schedule(candidates, constraints, duration_fn) 初排
  → 编排层：查相邻段和住宿往返的高德耗时
  → 同一 schedule 函数前向检查，最多两轮修正
  → 一份按天行程 → amapTaskData / 地图 HTML / 规范行程表
  → 原有无工具汇总模型成文
  → 按标题替换行程表、补事实与假设说明、执行既有闸门
  → 保存既有方案文件与快照，返回 final
```

主智能体继续调度；票务子智能体继续查询 12306。Tavily 密钥仅由编排层读取，不进入地图 shell、浏览器或模型消息。地图子智能体不负责选择查询、抽取闭馆规则或给来源定级。

### 3.1 地图子智能体的输出

保留现有只读高德 skill 和收窄的 shell 环境。修改地图提示词，让子智能体返回一份可解析的候选 JSON，至少包含：

| 字段 | 来源或用途 |
| --- | --- |
| poi_id、name、city、lng、lat | 高德 POI 身份与坐标 |
| place_type | 景点、博物馆、公园等场所类型，用于搜索优先级和游览时长 |
| must_visit | 用户是否明确必去；不能仅因推荐度高就设为必去 |
| reason | 简短推荐理由 |

通过现有 dispatch.map_chunks 接收子智能体任务结果，按 JSON 解析；可以去除单一 Markdown 代码围栏，不从任意自然语言中猜取坐标。

编排层使用现有 _search() 校验候选的城市和地点身份，并保留高德 ID 与类型。地点不明确时保留待定位说明；返回不了可验证候选时，由现有高德检索兜底。模型记忆坐标不能成为正式地图点。

服务端接管最终 HTML 生成，Node skill 继续承担候选检索。这样第一阶段就能停止“模型写 HTML 后再重排”的双重排程。

## 4. 最小输入与数据结构

### 4.1 只增加三个槽位

| 字段 | 取值 | 缺省 |
| --- | --- | --- |
| must_visit | 明确必去的景点名称列表 | 空列表 |
| avoid | 明确排除的景点或活动列表 | 空列表 |
| transport_mode | public_transit / driving / walking | public_transit |

这三个字段必须同步到 TravelSlots、ExtractedSlots、抽取提示、规范化、修订合并和前端确认卡回传。用户没有提供字段与明确清空列表必须区分：未提供不覆盖旧值，明确清空允许删除原要求。

每日 09:00—18:00 使用常量，在需求摘要中说明。原有出发地、目的地、日期和多日住宿地澄清规则保持现状。

用户原话中的“14:00 到”“已预约 10:00”等内容保留在需求和偏好说明中，不自动变成已验证时段，也不新增追问。输出必须明确这些要求尚未纳入结构化时间校验，不能声称默认时间表已满足它们。首末日与跨城交通衔接同样保留候选性质。

### 4.2 三块规划数据

沿用现有 dict/list 和已有验证方式，不另建完整产物类型体系。函数边界只检查实际使用的字段：

```text
candidates[]
  poi_id / name / city / lng / lat / place_type
  must_visit / reason / visit_minutes

constraints
  date / days / city / lodging / transport_mode / must_visit / avoid
  facts[]
    poi_id / kind / value / date_or_weekday
    quote / source_id / status
    source_url / source_title / source_summary / retrieved_at

days[]
  date / day / items[] / legs[] / notes[]
```

constraints 中的日期、天数和住宿来自现有槽位，供纯函数建立日历和起终点；必去与排除要求在槽位贯通后以确认值为准，不能由模型推荐覆盖。facts 是排程可能使用的运营事实。来源摘要直接随事实保存，source_id 由编排层生成、回填和校验，不交给模型。

行程项至少含景点 ID、开始/结束时间和游览分钟数。交通段至少含起终点 ID、mode、duration_seconds 和查询时间；未知耗时为 null，并附未核实说明。

仅保留两个整体状态：

- facts_status：checked / partial / unavailable。第三方结果或未覆盖的关键规则存在时为 partial，这是正常结果。
- schedule_status：checked_under_assumptions / candidate / conflict。未知交通、关键运营条件未核实或原话时间要求未验证时为 candidate；明确必去冲突为 conflict。

checked_under_assumptions 只表示本次已知规则和路线通过检查，不能表达已预约或未来路况保证不变。HTML 是否生成继续由现有地图状态表达，不代替这两个判断。

### 4.3 排程常量

| 常量 | 初值 |
| --- | --- |
| 每日可用时间 | 09:00—18:00 |
| 午餐 | 60 分钟 |
| 景点切换缓冲 | 15 分钟 |
| 每日机动时间 | 30 分钟 |
| 类别游览时长 | 大型博物馆 150 分钟、一般景点 90 分钟、公园街区 60 分钟 |

用户明确游览时长时优先采用其要求，否则按类别估计并披露。切换缓冲只额外计算一次，不重复累加公交结果已经包含的步行、换乘时间。每日机动时间保留在时间预算中，不靠压缩缓冲凑景点数。

## 5. 编排层 Tavily 检索

### 5.1 固定查询与候选优先级

编排层按“必去优先、博物馆等有明确营业限制的场所优先、再按候选顺序”确定搜索对象。同一候选仅查询一次，失败重试除外。

查询模板为“城市＋景点名＋旅行日期＋开放时间 预约 闭馆”。查询内容来自校验后的候选与槽位，不让模型自行编写。

使用 general、basic、最多 5 条结果；关闭自动答案、原始全文和自动参数调整。首版不按域名过滤搜索结果。携程、美团、可索引公众号或其他攻略结果可以进入展示材料，但不因此成为排程硬限制。

同一个来源若明确覆盖多个出行日，可以复用；最多 6 次搜索不代表所有候选已核实。多日方案必须显示未覆盖项。

### 5.2 预算与 HTTP 行为

| 项目 | 规则 |
| --- | --- |
| 实际尝试次数 | 最多 6 次，失败和重试都计入 |
| 单次超时 | 最多 8 秒，且不超过共同窗口剩余时间 |
| 共同截止时间 | 从编排层进入搜索阶段起计 30 秒，查询间隙不重置 |
| 并发 | 最多 2 个请求 |
| 重试 | 单个失败查询最多一次，总次数仍不超过 6 |
| 无 Key、401、额度不足 | 直接降级，不重试 |
| 重复请求 | 请求内复用同一城市、POI、日期的结果，不再次外呼 |
| 取消 | 停止新请求，取消并回收在途异步请求 |

请求计数和截止时间由请求局部对象维护，不能使用进程全局次数，也不能只写在提示词里。使用已安装异步 HTTP 客户端直接调用 Tavily；外层超时不应留下继续运行的网络任务。

保存请求次数、失败原因和供应商原始用量即可。供应商返回缺失不填成零用量；已发出后取消的请求仍可能计费。

## 6. 证据成为硬约束的门槛

### 6.1 每条证据的处理

1. 编排层保存返回的标题、URL、摘要和检索时间，并生成 source_id。
2. 以完整主机名匹配一份人工核对过的小名单。名单可包含已核实的景区、场馆或文旅网站，不只看域名后缀。
3. 使用少量明确规则识别“周一闭馆”、明确日期关闭、开放时间段和最晚入场。解析结果必须能对应同一景点。
4. quote 必须是保存的 source_summary 的非空连续子串；不能由模型改写成一句意思近似的话。
5. 常规星期规则展开到实际出行日期；明确日期规则只用于同一日期。日期、场馆身份或例外条件无法确定时，保持待核实。
6. 以上条件全部满足，且原文语义完整明确，才把 status 设为 hard；否则为 pending，不限制排期。

原文片段存在只是必要条件。例如“周一不闭馆”“周一闭馆，节假日除外”不能截掉否定或例外后解析成无条件“周一闭馆”。出现不能处理的否定、例外或互相冲突规则时，整条降为待核实。

首版直接忽略“本周一”“明日”等相对日期，不推断页面发布时间。网页摘要截断导致规则不完整，也保持 pending。

### 6.2 首版参与排程的规则

| kind | 可接受的明确表达 | 排程作用 |
| --- | --- | --- |
| closed_weekday | 常规每周一闭馆，且没有未解释例外 | 对应星期禁排 |
| closed_date | 明确 YYYY-MM-DD 闭馆或关闭 | 对应日期禁排 |
| opening_hours | 明确营业时间，可有午间休息 | 完整游览必须落在开放窗口 |
| last_entry | 明确最后入场时间 | 开始入场不得晚于该时间 |

“需要预约”和第三方攻略保留为提示。没有真实预约确认机制时，不把它们转换成已确认预约时段，也不声称可保证入场。

### 6.3 未核实信息的输出

非名单域名、原文不完整、相对日期、来源冲突或搜索预算不足，均不禁止景点排期，但应展示材料链接和“开放规则未核实”。

已确认的闭馆事实仍必须改变主路线。不能一边标待核实，一边把已经确定关闭的景点排进去。

来源链接与摘要只作为数据处理，继续采用现有 HTML/Markdown 净化；密钥、认证头不写入日志或产物。

## 7. 排程纯函数与交通查询

### 7.1 函数边界

在 planner/route_plan.py 中实现：

```python
schedule(candidates, constraints, duration_fn) -> days
```

函数不发 HTTP、不读环境变量、不改全局缓存。duration_fn 是确定性的只读查表函数，以起终点、模式和出发时段查已经取得的耗时；缺失时返回 None。单测注入固定表，整个排程可离线复现。

编排层负责外呼、保存本次路线结果，并把表交给 schedule。纯函数先给出初排和需要的相邻段；编排层补查后再调用它。调用轮次受限，不通过“注入一个现场发 HTTP 的函数”把副作用藏进排程器。

### 7.2 有限排程过程

1. 按 POI 身份去重，去掉明确排除项，保留必去标记。
2. 从出行日期展开天数和星期，应用 hard 关闭规则。
3. 先给开放日期受限的必去项安排日期；其余候选用现有方位初排。
4. 每天不超过 4 个点时枚举顺序；多于 4 个时采用方位和近邻初排，不做全局排列。
5. 用交通耗时前向计算到达、等待、游览、午餐和返回住宿时间。
6. 排不下时先日内换序或换日，再删减非必去项，最多两轮修正。
7. 返回最终行程和移动、删减、未核实原因；不能安排的必去项必须明确列出冲突。

不再按“离酒店近”直接裁掉远处必去点。4 是枚举规模的分界，不是每日最低或最高景点数的硬要求。

### 7.3 前向时间检查

```text
到达 = 上一项结束 + 已知交通耗时 + 切换缓冲
开始 = max(到达, 开放窗口起点)
结束 = 开始 + 游览时长

检查完整游览窗口、最晚入场、午餐与机动预留，
并把返回住宿交通纳入每日 18:00 前的预算。
```

午间 12:00—13:30 不开放时，不能把 11:30—13:00 视为可行游览。等待开门占用当天时间，不能从预算里消失。

已知耗时导致超时，可以删减可选项；未知耗时不能当作 0，也不能直接判整天失败。未知段可保留明确标注的时间预留，放在 notes 中，不填写为真实接口耗时；受其影响的日程保持 candidate，不能给出“已核实精确到达”的表述。

### 7.4 复用现有高德请求

在 planner/map_fallback.py 的 _search() 旁增加同样风格的路线请求，返回规范化的 duration_seconds、distance 和 mode。复用现有 Key 读取方式，明确当前 API 的返回字段；公交无结果或没有 duration 就返回未知。

路线查询只查相邻景点和住宿往返。典型两日、每天 3 个点约有 8 条交通段，加少量步行/公交比较和修正，一般为十来次；不构造全候选距离矩阵。

每次规划的 60 次请求、60 秒是保护上限，不是填满目标。单次请求最多 6 秒，受剩余窗口限制；不进行多轮后台重试。HTTP 在编排层执行；已有同步请求需离开事件循环运行，并保留有限底层超时。不能把取消线程等待误报为已取消底层网络请求，未完成返回不得再写入已结束请求的结果。

请求内缓存至少区分起点、终点、方向、交通模式、日期与出发时段；换日或出发时段变化后，受影响段不能直接复用。单位转换统一在请求适配处处理。

默认公共交通＋步行：有高德结果且步行不超过 20 分钟时可选步行，否则用公交。明确自驾用 driving。公交失败标未核实，不用直线距离换算耗时。

## 8. 地图与正文使用同一份列表

planner/map_fallback.py 的 render_map_html() 继续承载 HTML 渲染；输入改由规范 days 投影成现有 amapTaskData，保留每项 day 和真实 routeType。

路线、地图和行程表不再从各自的模型输出决定顺序。替代建议、未采用项写在说明中，不混入当前主路线。

无工具汇总模型继续写六章节。模型成文结束后，按二级标题“行程表”定位到下一个二级标题，用程序表格替换该章正文；如果出现多份行程表章节，应收敛成一份。缺标题时复用既有章节重试，仍失败则程序装配该章节。

替换应作用于重试成功或降级后的最终文本，再执行章节和票务闸门。前端流式内容仍是草稿，final.content 覆盖为规范版本。

事实提示、默认时间、删减原因和待核实清单用短句从结果生成。最终检查地图与表格的日期、POI 顺序、交通模式一致；不能只比较是否生成文件。

## 9. 确认卡、快照与修订

这部分在主路线已经能躲开闭馆日之后实施。

确认卡提交时保留当前完整槽位，再覆盖用户编辑字段；must_visit、avoid、transport_mode 不能因界面没有对应输入框而消失。服务端在整条抽取、合并、保存链路上透传这三个字段。

现有快照增加 schema_version=2 和三块规划数据、facts_status、schedule_status。完整内容仍写现有快照文件，SQLite 沿用原表与产物路径。

| 修订 | 行为 |
| --- | --- |
| 只改措辞 | 复用原 days 与地图，只替换解释文字和规范行程表，不重新搜索或排程 |
| 改日期 | 重建星期和日期约束，并重查相关运营事实及交通 |
| 增删景点 | 新候选走同一取证门槛，受影响日期重新排程 |
| 改住宿或交通模式 | 复用仍适用的运营事实，重查相邻交通与住宿往返 |
| 旧快照缺少结构化数据 | 可展示旧文案；需要重排时重新生成候选，不把旧 HTML 当作已核实规则 |

复用证据时显示原检索时间，不伪称刚刚查询。日期变化不沿用不适用的关闭规则。

## 10. 降级行为

| 情况 | 行为 |
| --- | --- |
| 无 Key、401、额度不足 | 继续出行程，开放规则标未核实 |
| 6 次或 30 秒用尽 | 停止搜索，保留已有约束和未覆盖说明 |
| 摘要无法通过证据门槛 | pending，不禁止排期，不包装成硬事实 |
| 官方规则无法消解冲突 | 待核实并展示冲突，不武断选一条 |
| 高德候选无法定位 | 不猜坐标；保留无法定位说明，按已有检索能力兜底 |
| 部分公交耗时未知 | 保留当日候选，标明交通未核实 |
| 必去项确定不可安排 | 明确冲突和原因，不能静默删掉或强塞 |
| 汇总失败 | 在现有降级文案中仍装配可靠的程序行程表 |
| 用户取消 | 停止新增工作；有限在途请求不再发布或回写最终方案 |

ensure_route_map() 的兜底改成复用同一候选、schedule 和渲染函数，避免正常与兜底采用不同分天规则。

## 12. 四阶段落地与验收

### 阶段 1：事实来源和纯排程闭环

先停止无条件 reorder_existing_map()。地图智能体交候选，服务端用 schedule 生成一份行程和地图。以固定证据和注入耗时表验收，不接 Tavily、不发路线 HTTP。

必须用下节两日场景证明：周一闭馆的必去馆挪到周二、远的非必去点因时间被删并写原因、必去项不被裁剪、交通模式保留、地图和表格一致。T01、T05、T07、T10 必须通过。

这是一项独立交付，搜索没有完成也不能阻止这些修复验收。

### 阶段 2：编排层受控搜索

固定模板查询并保存摘要。证据门槛通过才能进入 hard 约束，地图子智能体不接触搜索工具或来源 ID。

验收无 Key 可启动、失败正常降级、请求上限有效，以及一条真实可核对的闭馆证据能改变主路线。facts_status=partial 不视为失败。

### 阶段 3：真实交通与有限修正

在现有高德 HTTP 代码旁补路线耗时，编排层先查表所需相邻段再前向校验，最多两轮换序、换日或删减。

验收住宿往返、午餐缓冲计时，公交未知不填假值、不使整天直接失败；两日用例的查询量维持相邻段级别。

### 阶段 4：确认卡与修订持久化

贯通三个槽位的回传、schema_version、完整快照和只改措辞不重排。按日期、住宿、模式变化重新计算所需部分。

完成阶段验收后再进行在线效果对照；各阶段都不以“接口能调用”代替闭馆和一致性回归。

## 13. 首个闭环验收示例

以下景点、规则和耗时均为虚构测试输入，不代表真实公告。

输入：2026-11-02 起两日，住同一酒店，甲博物馆必去，公共交通。使用默认 09:00—18:00。

固定证据：甲周一闭馆、周二 09:00—17:00 开放、游览 150 分钟；乙公园和丙街区各游览 90 分钟。远郊丁游览 180 分钟，且不是必去；注入表规定酒店及其他候选与丁之间的单程耗时均为 180 分钟，计入午餐与机动后，即使单独安排一天也超出预算。

注入耗时表后，输出应满足：

| 日期 | 程序行程示意 | 说明 |
| --- | --- | --- |
| 11-02 周一 | 酒店 09:00 → 交通 30 分钟 → 乙 09:30—11:00 → 切换 15 分钟＋交通 30 分钟 → 午餐 11:45—12:45 → 丙 12:45—14:15 → 切换 15 分钟＋返程 30 分钟 → 酒店 15:00 | 甲不能在此日；丁因时间不足删减并写原因 |
| 11-03 周二 | 酒店 09:00 → 交通 30 分钟 → 甲 09:30—12:00 → 午餐 12:00—13:00 → 切换 15 分钟＋返程 30 分钟 → 酒店 13:45 | 必去项保留，含午餐、切换和返住宿后仍留有每日机动时间 |

测试只证明给定证据和假设下的排程正确。生产中如果原文提到尚未验证的抵离或预约要求，另加候选性质说明；不能借此测试声称相关条件已核实。

## 14. 测试与效果评估

### 14.1 离线回归

默认沿用 pytest -q -m "not integration"。时间预算测试使用可控时钟与 mock HTTP，不实际等满 30 秒。以下编号保留与原验收重点的对应关系：

| 编号 | 场景 | 必须断言 |
| --- | --- | --- |
| T01 | 两日＋必去馆周一关闭 | 移到开放日或明确冲突，不排在闭馆日 |
| T02 | 明确日期关闭，另有不完整例外 | 只采用能够确定适用日期的规则，其他待核实 |
| T03 | 原文子串存在但有否定或例外 | 不误提取无条件硬约束 |
| T05 | 午间休息与最晚入场 | 完整游览处于允许窗口，入场不超限制 |
| T06 | 可选景点使当天超过时间 | 换序/换日或删减，不压缩固定缓冲凑数量 |
| T07 | 远处必去点＋近处可选点 | 必去点不被按距离静默裁掉 |
| T08 | 默认时间及原文中未验证时刻 | 不新增追问，公开默认值与未校验限制 |
| T10 | 公交、自驾、短程步行 | 地图和表格保留正确模式 |
| T11 | 不同方向、日期或出发时段 | 耗时缓存不错误命中 |
| T12 | 公交无结果或耗时为空 | null＋未核实；不填 0，不直接判全天失败 |
| T13 | 并发请求和失败重试 | 实际 Tavily 尝试总数不超过 6 |
| T14 | 共同 30 秒截止 | 不发新请求，已结束规划不接收迟到结果 |
| T15 | 无 Key、401、额度不足 | 正常出候选，开放规则未核实，无无限重试 |
| T16 | 错误来源、摘要子串缺失、相对日期 | pending；名单不用于过滤网页搜索 |
| T17 | 后处理和自由成文可能改变顺序 | 最终地图和行程表来自同一 days |
| T18 | 只改措辞 | 不重新搜索、不重排，仍使用原 days |
| T19 | 改日期或交通方式 | 重算受影响约束和路线 |
| T20 | 旧快照 | 不把旧 HTML 当作硬证据 |
| T21 | 兜底和取消 | 使用同一排程规则，取消后不再发布成功结果 |
| T22 | 确认卡和修订清空列表 | 新字段不丢失，明确清空与缺失区分 |

硬验收：已知闭馆冲突为 0、必去静默丢失为 0、地图/表格日期顺序模式一致率 100%、hard 规则全部通过域名/子串/日期/语义门槛、搜索不超预算。对已知规则检查通过与整条方案具备完整事实依据分别统计，不能靠排除未知项虚报可执行率。

### 14.2 少量真实对照

复用 evals/run_golden.py 和现有耗时记录，比较当前基线、新排程但不启用 Tavily、新排程启用 Tavily三个版本。相同输入和模型参数交错运行，保留实际证据时间；历史旧流水线数字不直接当作新基线。

先覆盖周一闭馆、远郊点、自驾、必去冲突、默认时间、改日期和无 Key等场景。对可正常外呼的需求重复少量次数，失败场景优先离线注入。

报告只需列出：硬冲突、未核实比例、必去保留与冲突披露、交通请求数、搜索请求数和原始用量、整体及阶段耗时、地图/表格一致性。原文事实是否被正确解释需要人工核对，不能仅凭模型评分。

成功的标志是一条可靠事实改变了原来错误的主路线，并且没有破坏必去项与数据一致性；多几个链接不算效果提升。
