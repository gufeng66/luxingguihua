# ADR-5：方案依据与对象角色

## 状态

接受

## 背景

截图里那一屏告警几乎都来自同一个毛病：把不同层的东西当成同一层。

- 查到了 20 条座席事实，就在页面上说「票务已核实」——把「查询到了」直接当成「已适用于本次区间与日期」。
- 把站点查询的响应当车次解析，报出两条「票务响应无法识别」。
- 模型给「上海站」标了 `must_visit=true`，同一个上海站既当住宿锚点又当必去景点，然后说「必去项未能排入」。
- 住宿只写到「上海站附近」，于是要么被当成已确认酒店，要么被当成景点去检索。
- 车次明明有 15:43 出发时刻，首日却按 09:00 从住宿地出发排了一整天。

每条单看都能补一个 if，合起来就是一个结论：事实、适用性、依据、安排必须分开记，角色也必须显式。

## 决策

### 一、票务链分四层，不跳层

| 层 | 谁产生 | 能说明什么 |
|----|--------|------------|
| 查询事实 | `parse_ticket_payload` | 工具原始响应里有这些行 |
| 适用事实 | `_annotate`（`direction` / `station_match` / `applied` / `reason`） | 这些行里哪些对本次行程成立 |
| 规划依据 | `choose_plan_basis` | 按哪一趟算首末日的抵离时刻 |
| 实际出行安排 | `schedule` 排出的 `days` | 每天几点到几点、走哪几段路 |

`quality.checks.ticket` 只认**适用事实**。查到了但一行都不适用时状态是 `unverified` 并给出 `ticket_not_applicable` 和原因，而不是把「查到了」包装成「核实了」。解析器只处理车次结果工具（`TRAIN_RESULT_TOOLS`）；站点、时刻表这类工具的响应不进车次解析，也就不再产生假的车次错误。尚未启用解析的工具只写 `notes`，不当告警。

**适用范围（补充说明）**：本节的两条判据在**修订复用**场景下依然成立，容易被误读成另一种口径，单独说明：

- `checks.ticket` 的判据是「**本轮是否核实过**」，不是「有没有车次、事实条数够不够」。复用父方案的票务事实时状态仍是 `unverified`，事实再多、`applied=True` 的条数再多也不升级——那些行证明的是上一轮查得到，不是这一轮核实过。复用只影响正文措辞（写明沿用上次查询及其查询时间、余票未刷新），不改变 `checks` 的取值。
- 复用链不能直接采信父方案的 `applied` / `direction` / `reason`：这三者是按**父方案的日期与区间**算出来的。进入本轮规划依据之前必须按当前 `expect_date` / `return_date` 重新验证一遍（方向、是否适用、不适用原因），通过之后才交给 `choose_plan_basis` 收敛成依据。先按旧结论挑车、再补验证，等于把已经不成立的事实当成依据。
- 这条只约束「复用」这一层。`ticket_and_map` 重新查询的路径不涉及继承，按本节原有口径判即可。

**刷新语义补充**：重查后只能保留“用户此前选过哪趟车”的选择意图，不能保留旧事实字段。依据按方向、日期、出发站、到达站和车次从本轮适用事实重建，时刻、座席、价格、余票和来源都来自新事实。可售只认明确“有票”或正的剩余张数；无票和余票未知仍是查询事实，却不能当作排程依据。用户点名车在刷新后无票或不适用时，当前依据置空而非静默换车；系统推荐失效时才可以按本轮可售事实重新推荐。

### 二、缓冲是假设，不是事实

`RAIL_TRANSFER_MIN = 40`、`RAIL_BOARD_MIN = 30` 是规划假设，用来把「15:27 抵达」换算成「16:07 开始」。它们会随窗口文案一起说明，不进入车次事实。

对应地，窗口有四种状态而不是一个时间区间：`default`（没有依据，用默认 09:00–18:00）、`constrained`（按抵离时刻收窄）、`unknown`（有依据但缺时刻，不假装知道）、`unavailable`（当天窗口不足，保留为「主要用于抵离」的一天）。**绝不写 `start or DAY_START`**——那等于把未知当已知。

`not_constrained` 的边界要说清：只有**不需要铁路**（明确自驾/步行、同城、或不需要返程）时才落到 `not_constrained`，这时才允许默认窗口。需要铁路却没拿到可用车次依据时是 `unknown`（首日最早开始时间、末日最晚结束时间都未知），不能因为「没查票」就退回默认 09:00–18:00。

### 三、`must_visit` 只在可信边界收敛

必去项只来自用户原话。候选池自带的 `must_visit` 标记不被采纳：模型把「上海站」标成必去，是模型的理解，不是用户的要求。住宿 POI、车站、酒店类型的地点一律不进景点候选池，也不出现在开放规则的分母里。

未定位项带 `kind`（`sight` / `must_visit` / `lodging` / `station`）。只有 `must_visit` 会让排程判 `conflict`；普通景点没定位只是「没进候选」，不该升级成「必去项无法排入」。

### 四、区域住宿可以规划，但不能当锚点

住宿是三态（`exact` / `area` / `unresolved`）加精度字段，不是字符串：

- `exact`：用户给了具体酒店且高德能对上。可以当出发与返回锚点。
- `area`：只到「上海站附近」。锚点取该区域 POI，但**不宣称已确认酒店**，留一项待确认。
- `unresolved`：给了具体酒店但匹配不上。按目的地中心暂代并如实说明。

不强迫用户先订酒店——区域住宿照样能出可行行程；但也不能把上海站的坐标包装成「已确认酒店」。用户明确选「按该区域参考规划」之后，这件事变成已确认，不再反复追问。

**适用范围（补充说明）**：本节标题「不能当锚点」应读作「不能当**已确认酒店**的锚点」，不是「区域住宿不能参与排程」。本决策正文已授权 `area` 精度取该区域的 POI 作为**参考锚点**来形成排程闭环，前提是三条同时成立：

- 锚点必须标注 `precision="area"`，与 `exact` 在数据上区分得开；
- 行程正文写明「以上海南站为住宿区域参考点，酒店到参考点的接驳待定」，不得据此宣称已确认酒店；
- 参考锚点建立之后，往返两段住宿接驳必须进入路线查询与耗时统计，不能因为是「参考点」就把接驳排除在分母之外。

`lodging_loop_verified` 仍然只对 `exact` 为真——它表达的是「已完成住宿闭环核实」，参考锚点不满足这一点。参考锚点是否建立，用另一个字段（`lodging_anchor_ready`，或 `lodging_state` 里的锚点状态）单独表达，不要让同一个布尔量既表示「有没有锚点」又表示「是不是已确认酒店」。

### 五、路线结果只能标参考

高德路线查询有四态：`ok` / `no_route` / `failed` / `not_queried`。`duration` 为 0 或缺失归到 `no_route`，不再当成「0 分钟」。失败原因（`budget` / `rate_limit` / `request_failed` / `no_route`）要保留到告警和技术详情里，「部分交通耗时未核实」后面得能看见为什么。

次数和时间同时预留：POI 检索与开放规则取证先扣掉必要路段所需的额度，必要时路线查询走 `protected` 尝试，避免候选检索把路线额度吃光。这不增加总预算，只调整优先级。

## 后果

- 告警数量会下降，但下降的原因是误报被消除，不是把校验放宽。
- 页面上会出现「待你确认」的状态：方案已生成，但确认之前只是草稿。`quality.status` 因此可能停在 `partial`，而 `checks` 保持真实核实结果，不为了降状态伪造 `unverified`。`checks.travel_time` 新增 `reference` 档：路线 `ok` 只说明「取得了有效结果」，未带日期/时段时只能算参考，整体状态至少 `partial`；只有另有完整适用性依据时才升为 `verified`。
- 旧快照（`schema_version < 4`）缺新字段。`load_snapshot_v4` 用旧 `ticket_raw` 回填时刻、补空的 `request_context`，并标 `legacy` 与 `itinerary_needs_recheck=True`。`itinerary_needs_recheck` 是持久标记：旧口径行程只有真正按当前规则重建才会解除；文件格式升级到 v4、或者本轮有没有重新排程，都不能单独证明行程已核实。
- `mode="revise"` 不再回传整份旧槽位；`mode="confirm"` 先与上一版求差再决定重跑哪几步。确认状态落 `request_context`，隔轮修订也不会丢。
- 跨城方式与往返需求是 `request_context.intercity_mode` / `return_required`，不同于 `slots.transport_mode` 的市内游览方式。`initial` / `revision` 的本轮原话可建立或覆盖该意图；确认表单回传的旧原话为 `background`，只能作历史背景，实际表单改动优先。跨城意图变化会使票务复用与旧依据失效。
- `request_context.cleared` 是累计撤销状态。撤销人数、预算口径或住宿口径后，历史原话、继承偏好和旧上下文不得回填；只有新原话或表单再次明确赋值才解除。撤销住宿口径同时清空住宿类型并触发地图重算。
