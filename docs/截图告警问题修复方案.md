## 1. 目标与成功标准

**目标**：结果页只报告真实缺项；需要用户决定的事成为结构化数据并可操作；时间类结论必须有事实依据。

**成功标准**（基准快照 `workspace/results/snapshots/4a10bad9-171b-40ba-b695-6eaa589e75d2.json`）：

1. **A1 验收（只做工具分流时）**：`raw-1 get-stations-code-in-city`、`raw-2 get-station-code-of-citys` 不再产生「票务响应无法识别」；`raw-3 get-tickets` 仍解析出 20 条座席事实（5 趟车 × 4 种座席）。
2. **A2 验收（加入适用性判断后）**：每条车次记录都有明确的保留或排除理由（含同城其他车站）；**不固定事实数量**，允许因区间/方向/座席不适用而少于 20 条，但每一条的变化都能在快照 `ticket_applicability` 里查到原因。
3. **住宿区域不进入景点开放规则分母**，也不因住宿问题产生景点开放告警；**其他实际景点的开放规则缺失继续报告**。
4. 上海站不再同时是住宿锚点又是必去景点；`must_visit` 只来自用户槽位。
5. 交通覆盖率的分子分母按真实路段统计：截图那次应显示已有查询结果的路段数 > 0，而不是 `0/14`；且这些路段只标为「参考耗时」，不冒充已核实。
6. 首日不早于所采用车次的抵达时间加接驳；未取得可用抵达时刻时，**不输出已核实的首日精确起始时刻**；跨日抵达时，抵达日之前的日期不安排目的地游览。
7. 「查询依据」按查询记录聚合：显示「1 次票务查询（get-tickets），20 条座席价格记录」，其余 2 次站点查询各自成条；相同参数查询两次就显示两次。
8. 顶部状态随质量变化，有待确认项时显示「已生成，待补充」，不得显示「完成核验」。

**不做**：不新增依赖；不改 `TravelSlots` 字段集；不延长 240 秒总预算；不放松校验；不新增工作流框架；不宣称已购票；不为了消除告警而删除真实缺项。

## 2. 事实与依据的分层

三层必须在数据里分开，否则后面所有时间计算都站不住：

| 层 | 含义 | 落点 |
|---|---|---|
| 查询事实 `facts_parsed` | 某次工具查询返回并成功解析出的车次/座席/价格/时刻 | `planner/ticket_facts.py`，已有 |
| **本方案适用事实** `facts_applicable` | `facts_parsed` 中「方向 + 区间 + 日期」都适用于本方案的那些记录 | 新增，`facts_from_records` 返回的第二份列表 |
| 规划依据 `plan_basis` | 本方案采用哪一趟车作为排程依据 | 新增，写入 `constraints["plan_basis"]` 与快照 `request_context.plan_basis` |
| 实际出行安排 | 用户已购买/已确认的车次 | **本项目不产生**。正文措辞固定为「该车次仅作为规划依据，购票状态未知。」或「按你指定的车次…规划，购票状态未知。」 |

**停用第二稿的措辞**：「未购票」。系统不知道用户是否已自行购票。

**`plan_basis` 形状**（dict，不新增 pydantic 模型，返回值形状固定为两条）：

```python
plan_basis = {
    "outbound": None,   # 或一条 basis
    "inbound": None,
}

# 单条 basis
{
  "train_no": "G1813",
  "depart_date": "2026-11-07",          # 未知为 None
  "arrive_date": "2026-11-07",          # 未知为 None；见 3.3 的推导规则
  "arrive_date_source": "tool" | "derived_from_lishi" | None,
  "depart": "09:35", "arrive": "15:27", # 未知为 None
  "from_station": "新乡东", "to_station": "上海虹桥",
  "lishi": "05:52",
  "station_match": "exact" | "same_city",
  "seats": [{"seat": "二等座", "price": 493.0, "availability": "有票", "bookable": True}, ...],
  "source_id": "raw-3",
  "origin": "user_selected" | "proposed",
  "reason": "用户原话指定 G1813" | "系统建议：当日最早抵达的可售车次",
}
```

### 2.1 选择规则（`choose_plan_basis(facts_applicable, *, query, direction)`）

排序前必须先做适用性判断，不能拿未处理方向的记录排序：

1. **归并**：同一 `(train_no, depart_date, from_station, to_station)` 的多种座席归并为一条车次，座席进 `seats`。避免 4 种座席被当成 4 个候选。
2. **可用座席**：`bookable = availability 不含「无票」`。全部座席无票 → 该车次不进系统建议（用户点名的除外）。
3. **日期**：`arrive_date` 未知的事实**不参加排序**（不能假设当天到达）。
4. **去程（outbound）**：在可用车次中按 `(arrive, price_min)` 排序，取第一条 → `origin="proposed"`，`reason="系统建议：当日最早抵达的可售车次"`。
5. **返程（inbound）**：**不照搬去程规则**。
   - 用户原话给出了离开时间倾向（「晚上返程」「下午回来」「别太晚」等）→ 在该倾向范围内取最接近的一条；
   - 没有相关条件 → `inbound = None`，`reason="未指定返程时间，末日窗口按默认结束时间规划（假设）"`。
   - **禁止**为了凑一个返程依据而自动选最早返程，从而压缩游览时间。
6. **用户点名**：原话出现车次号且**是选择语境**才判 `origin="user_selected"`。否定与比较语境不算选择，并记录原因：
   - 不判选：`不要 G1951`、`别坐 G2811`、`除了 G1813`、`比较一下 G1951`、`G1951 还是 G2811`；
   - 判选：`就坐 G1813`、`坐 G1813 去`。
   - 实现：命中车次号的子句内检测否定/比较词表 `{"不要","别","除了","不用","比较","对比","还是","或者","看看"}`；命中则不判选。车次号抽取复用 `_PROSE_TRAIN`。
7. 无任何可用事实 → 两个方向都 `None`。

`choose_plan_basis` 的签名不因排序策略变化而改变；策略细节落在实现内。

## 3. 阶段 A · 票务解析与事实保真

### 3.1 A1 按工具分流，消除误报（`planner/ticket_facts.py`）

- 新增两个集合：
  - `TRAIN_RESULT_TOOLS = frozenset({"get-tickets"})` —— **已验证可解析**的车次结果工具；
  - `TICKET_TOOLS_UNPARSED = frozenset({"get-interline-tickets"})` —— 中转结果，**解析器未经验证，暂不启用**；
  - 其余（`get-current-date`、`get-stations-code-in-city`、`get-station-code-of-citys`、`get-station-code-by-names`、`get-station-by-telecode`、`get-train-route-stations`）只留原始记录。
- `facts_from_records`（`:257-279`）只对 `record.get("tool") in TRAIN_RESULT_TOOLS` 调 `parse_ticket_payload`。
- 未启用集合的记录：写入 `ticket_raw`，产 **note 而非 warning**：`{"code":"ticket_parser_not_enabled","tool":"get-interline-tickets","ref":"raw-5"}`，文案「中转查询结果已保存，但解析器尚未验证，不作为车次事实」。**不产生「票务响应无法识别」，也不计入 `ticket` 状态。**
- 诊断项追加 `"tool"` 与 `"ref"`（记录 ID）。
- 保留真实缺失：没有任何车次类记录 → `_ticket_status` 仍判 `unverified`，`collect_issues` 仍给「方案依赖铁路，但没有可引用的有效车次」。

**为什么必须这样改**：截图中两条「票务响应无法识别」分别来自站点列表和城市站点代码响应，它们本身是成功响应，只是返回结构不是车次结构；把它们送进车次解析器必然失败。

**中转工具的边界**：加入集合不等于支持。要启用 `get-interline-tickets`，先补一份真实响应样本（放 `planner/ticket_samples/`）与对应解析测试，再改集合；在此之前保持 note。

### 3.2 A2 记录自身区间 + 方向 + 日期三者匹配

第二稿只用「出发站命中出发城市」判断方向，`新乡→北京` 也会被判成去程。改为：

1. 逐条取 `record["arguments"]` 的 `date`/`fromStation`/`toStation`（候选字段名集合匹配）作为该记录的 `request_date`/`origin`/`destination`；缺失才回退到函数级参数；都缺 → 保留事实、`applicable_date=None`。
2. 逐行（解析后的 row）判定：
   - **outbound**：`row.origin` 命中用户出发地 **且** `row.destination` 命中目的地 **且** `row.depart_date == 出行日期`；
   - **inbound**：反向区间 **且** `row.depart_date == 返程日期`（`days` 推导，见 3.6）；
   - 否则 `direction=None`。
3. 城市匹配用「城市名去后缀后互相包含」的既有规则（`新乡` 命中 `新乡东`/`新乡南`），但**必须同时记录站点匹配度**：
   - `station_match="exact"`：`row.origin == 记录的 fromStation`；
   - `station_match="same_city"`：同城不同站（截图里 `新乡南` 的 4 条座席属于此类）；
   - `station_match="other"`：区间不匹配。
4. **适用性判定**（每条记录写进 `ticket_applicability`）：
   - `applied=True`：direction 命中、日期命中、`station_match ∈ {exact, same_city}`；
   - `applied=False` + `reason ∈ {"direction_mismatch","date_mismatch","station_other_city","no_arguments","unparsed_tool"}`。
   - `same_city` 允许进入适用事实（用户从「新乡」出发，新乡南同样是新乡的站），但 basis 与正文必须写实际站名；**不为了凑数把 other 城市放进来**。

**两套集合的用途分工**（这是第二稿最关键的漏项）：

| 用途 | 用哪一套 |
|---|---|
| `_ticket_status`（`quality.py:55-60`） | `facts_applicable` |
| `budget_markdown` 的城际交通计算 | `facts_applicable` |
| 正文车次白名单 `strip_unlisted_trains` | `facts_applicable` |
| `choose_plan_basis` | `facts_applicable` |
| 快照 `ticket_facts`（留档） | `facts_parsed`，每条带 `applied`/`reason` |
| 前端「查询依据」 | `ticket_raw` 记录数 + `facts_parsed` 统计 |

`_ticket_status` 同步改造：只对 `applied=True` 的事实判定；`facts_applicable` 为空但 `facts_parsed` 非空 → `unverified`，并产 issue「本次查到了车次，但区间/方向不适用于本方案」，而不是「票务响应无法识别」。

### 3.3 A3 保留抵离时刻与日期

两种响应格式都带时刻，当前都被丢弃：

- `_rows_from_text`（`:131-159`）：`current` 增加 `depart`/`arrive`；`_TEXT_TRAIN`（`:27-30`）扩展为**可选捕获** `历时`：
  `r"^(?P<train>[GDCZTK]\d{1,4}) (?P<origin>.+?)\(telecode:[^)]+\) -> (?P<dest>.+?)\(telecode:[^)]+\) (?P<depart>\d{2}:\d{2}) -> (?P<arrive>\d{2}:\d{2})(?: 历时：(?P<lishi>\d{2}:\d{2}))?"`

### 3.4 两个缓冲常量是假设

`planner/ticket_facts.py` 模块级常量（**暂不增加配置项**）：

```python
RAIL_BOARD_MIN = 30      # 进站缓冲（规划假设）
RAIL_TRANSFER_MIN = 40   # 车站到住宿/首个景点的接驳（规划假设）
```

它们必须出现在 `constraints["assumptions"]` 与正文「注意事项」里；**不得**写入 status 为 `verified` 的事实，也不得因为用了假设就把 `travel_time` 判成 verified。若某段接驳已取得真实路线耗时，用真实值替换对应常量并去掉该条假设。

### 3.5 铁路窗口 `rail_window()`

第二稿的 `travel_window` 用了 `transfer_minutes` 却没在签名里出现，且返回的是与日期无关的单一窗口，跨日无法表达。改为：

```python
def rail_window(plan_basis: dict, *, first_day: date, last_day: date,
                transfer_minutes: int | None = None) -> dict:
    """返回 {"outbound": {...}, "inbound": {...}, "assumptions": [...], "unverified": bool}"""
```

- `outbound`：
  - `arrive_date == first_day` 且 `arrive` 已知 → `earliest_start = arrive + (transfer_minutes if transfer_minutes is not None else RAIL_TRANSFER_MIN)`，`start_state="known"`；
  - `arrive` 未知 → `earliest_start=None`，`start_state="unknown"`；
  - `arrive_date > first_day` → 记录 `arrival_dates=[...]`，由 `day_window` 按天判不可用（见 5.2）。
- `inbound`：
  - `depart_date == last_day` 且 `depart` 已知 → `latest_end = depart - RAIL_BOARD_MIN - transfer`，`end_state="known"`；
  - `depart` 未知 → `latest_end=None`，`end_state="unknown"`；
  - **返程未查询或 basis 为 None** → `end_state="not_constrained"`（按默认结束时间规划，并注明是假设），**不是** `unknown`。
- 单日往返：`outbound` 与 `inbound` 同时落在同一天，`day_window` 取交集。
- 返回 `assumptions` 记录用了哪些缓冲（例如 `["RAIL_TRANSFER_MIN=40"]`），`unverified=True`。

### 3.6 返程日期与查询缺口（实测确认）

- 返程日期 = `date + (days - 1)`（`days` 默认 1）。
- **实测事实**：截图快照 `ticket_raw` 只有 3 条记录，其中车次查询只有 `get-tickets`（`fromStation=新乡东, toStation=上海`）**一次**，没有返程查询。`TICKET_AGENT_PROMPT`（`planner/ticket_agent.py:26-40`）也没有要求子智能体分别查去程与返程。
- 因此：**不给 `ticket_agent` 加「必须查返程」的硬要求**（会额外消耗一次外部调用与预算），但必须如实表达：`inbound.basis=None` + `inbound.end_state="not_constrained"`，正文写「未查询返程车次，末日可游览时间按默认结束时间规划，返程时间未知」。
- 若将来票务子任务确实查询了返程，则按 3.2 的 inbound 规则解析并生效，逻辑无需再改。

## 4. 阶段 B · 对象分类（成功与失败都覆盖）

### 4.1 B1 候选角色过滤顺序（先必去，再排住宿/接驳）

第二稿无条件丢弃 `role="station"`，会把用户明确想游览的车站一起删掉。固定顺序：

1. **先识别用户明确必去**：`must_set = constraints["must_visit"]`；`name in must_set or asked_name in must_set` 或别名命中（`_core_name` 去括号后相等）→ 保留，`role="visit"`、`must_visit=True`，**即使 `place_type` 是火车站**。
2. **再排除纯住宿与住宿接驳**：`role in {"lodging","lodging_area"}` 或 `place_type` 属 `住宿服务` 的项，不作为游览项。
3. **再排除接驳端点**：`role=="station"` 且未被第 1 步命中 → 只作为交通端点，不进候选池。
4. **最后通用过滤**：`avoid` 命中剔除；坐标非法剔除。

集中在 `planner/route_plan.py` 新增的 `sanitize_candidates(candidates, constraints) -> list[dict]`；`_mark`（`:488-494`）与 `_prepare`（`:497-521`）改为调用它，不再各自判断。`planner/map_fallback.py` 的 `picked["must_visit"]` 只表示「用户点名」的原始标记，最终以 `sanitize_candidates` 为准；`hints` 自带的 `must_visit` 视为不可信输入。

### 4.2 B2 住宿精度：先身份，后类型

第二稿「命中住宿服务 → `exact`」会替用户选中一家酒店（用户只说「上海站附近」，搜索恰好返回一家酒店）。改为按顺序判定：

1. **用户是否明确指定具体地点**：`lodging` 去掉区域词（`附近|周边|一带|区域|市中心`）后，若仍含具体住宿名（`酒店|宾馆|民宿|公寓|旅馆|客栈|路|弄|门牌`）或门牌号 → 候选 `exact`；
2. **是否明确接受区域规划**：本次请求带 `lodging_scope="area"` → `area`（不再追问）；
3. **查询结果号身份是否匹配**：命中 `poi` 的名称/别名与用户给的核心名一致（`_core_name` 相等或互相包含）才算「对上号」；只按关键词搜到一条**不构成匹配**；
4. **高德类型只作辅助**：`place_type` 属住宿服务 → 提升置信度；属交通设施/景点 → 降为 `area`；属其它（例如「地名地址信息」「商务住宅」）→ 保持 `unknown`。

`kind` 的实际取值：`exact` 只在前两条之一成立**且**第 3 条匹配成功时给出；

- 具体地址、亲友住址也可是精确住宿地，不要求 `place_type` 属住宿服务；
- `kind="area"`：用户只给区域（含已确认区域）；
- `kind="unresolved"`：用户给了具体地点但匹配失败。

**住宿三态与 code**（互不共用）：

| 状态 | 触发 | issue code | 文案 |

| 住宿区域待确认 | 只给区域，且本次未确认 `lodging_scope="area"` | `lodging_area_pending` | 「住宿只给到上海站一带，需你选择：填具体酒店，或按该区域参考规划」 |

## 5. 阶段 C · 排程窗口（未知不等于 09:00）

### 5.1 `day_window` 的状态机

```python
def day_window(day: date, constraints: dict) -> dict:
    """返回 {"state","start","end","reason","basis"}；start/end 为分钟或 None。
    state ∈ {"default","constrained","unknown","unavailable"}"""
```

判定表（**按当天真实日期**，不是「首日/末日」字符串）：

| 情况 | state | start / end | reason |
|---|---|---|---|
| 当天不涉及任何铁路限制 | `default` | `DAY_START` / `DAY_END` | `"默认窗口"` |
| 当天是出发日，且目的地尚未抵达（`arrive_date > day`） | `unavailable` | `None` / `None` | `"出发日，尚未抵达目的地"` |
| 当天是抵达日，抵达时刻已知 | `constrained` | `max(DAY_START, earliest_start)` / 默认或交集 | `"按 G1813 15:27 抵达 + 40 分钟接驳（假设）"` |
| 当天是抵达日，抵达时刻未知 | `unknown` | `None` / `None` | `"抵达时间未知"` |
| 当天是返程日，发车时刻已知 | `constrained` | 默认或交集 / `min(DAY_END, latest_end)` | `"按返程 Gxxxx 发车 - 30 分钟进站（假设）"` |
| 当天是返程日，发车时刻未知 | `unknown` | `None` / `None` | `"返程时间未知"` |
| 返程未查询（`not_constrained`） | `default` | `DAY_START` / `DAY_END` | `"未查询返程，按默认结束时间规划（假设）"` |
| `start >= end` | `unavailable` | `None` / `None` | `"抵离时间窗口不足"` |

**关键约束**：`unknown` 与 `unavailable` 都是 `start=None`，但含义不同，必须靠 `state` 区分；调用方读 `state` 决定「出不确定时刻的排程」还是「不安排游览」，**不允许**用 `start or DAY_START` 兜底。

`state="unknown"` 的处理：当天仍可参与排程，但所有条目不带 `start`/`end`（沿用现有 `unverified` 条目形态），`day["clock"]="unknown"`，正文写「当天时刻未核实」。

### 5.2 跨日

例：11-07 出发、11-08 上午抵达 →

- 11-07：`arrive_date(11-08) > 11-07` → `unavailable`，reason「出发日，尚未抵达目的地」；
- 11-08：`arrive_date == 11-08` 且抵达时刻已知 → `constrained`；
- 若抵达日期由 `lishi` 推导（`arrive_date_source="derived_from_lishi"`），正文注明「抵达日期由出发时刻与历时推算」。

### 5.3 必须改用的 7 处

| 位置 | 现在 | 改为 |
|---|---|---|
| `_simulate` `:357/384/391/392/423/425` | `DAY_START`/`DAY_END` | `win = day_window(day, constraints)`；`state != "default"` 时按 5.1 处理 |

### 5.4 空天保留且字段完整

## 9. 阶段 G · 查询预算与交通方式回退

### 9.1 walk 结果四分类（含第二稿漏掉的一条）

| 步行结果 | 后续 |
|---|---|
| `ok` 且 `<= WALK_MAX_SECONDS` | 用 walking，不查 transfer |
| `ok` 但 `> WALK_MAX_SECONDS` | 查 transfer |
| `no_route`（明确无步行路线） | **查 transfer** |
| `failed` / `not_queried`（鉴权、限流、预算耗尽） | 按失败类型停止，不做无意义重试 |

`result_state` 的四态定义：`ok`（有 `duration`）、`no_route`（响应成功但无路径或 `duration` 为 0/缺失）、`failed`（异常、HTTP 错误、`infocode` 非 0 且非限流）、`not_queried`（预算或截止时间不足，未发请求）。**`None` 不再笼统表示三者之一**。

### 9.2 两阶段查询在一次补查内完成

`assemble_itinerary` 的 `for _ in range(2)` 修正轮内，预取分两批：第 1 批 walking（全部相邻对）；第 2 批 transfer（仅需要者，`no_route`/超阈值/`failed` 之外的必需段）。**第二批必须在同一次 `fill_routes` 调用内完成**，避免「第二批刚补上换乘、重新排程又产生新边、修正轮次已结束」。

### 9.3 次数与时间同时预留

`planner/budget.py` 在 `RunBudget` 上增加阶段预留（不改总预算 240 秒）：

```python
reserve_attempts(remaining_rounds, adjacent_pairs)  # 每轮必要路段数 × 首选模式数
reserve_seconds(route_pairs)                        # 例如 min(60, 12 * pairs)
```

- POI 检索与开放规则取证使用 `available_attempts - reserve_attempts`、`work_left() - reserve_seconds`；
- 实际请求仍全部走 `note_attempt()` 总计数；
- 额度不足时的优先级（写进注释）：① 保留必去景点定位 → ② 保留必要路段首选模式 → ③ 保留必要路段换乘回退 → ④ 削减普通候选检索 → ⑤ 削减开放规则取证。
- 验证要覆盖「预算不足时的优先级」，不只验证「没有超额」：新用例让 `gather_facts` 故意慢（假 clock 每次 +25 秒），断言路线阶段仍拿到 ≥1 次尝试与 >0 的剩余时间。

### 9.4 候选截断提前到查询之前

`_PER_DAY` 已是 3、三日游泛搜上限已是 9，本次 11 个候选来自模型 hints —— 改泛搜 `limit` 无效。改为在 `assemble_itinerary` 入口截断 hints：

1. `must_visit` 命中的项全保留；
2. 其余按模型顺序取前 `min(len, days * _PER_DAY)` 条；
3. 剩余丢弃并记 `dropped(reason="候选过多，未检索")`；
4. 泛搜在截断之后执行。

### 9.5 失败原因保留

`fill_routes` 的 `error ∈ {"budget","rate_limit","request_failed","no_route"}`（`infocode=="10021"` 单独记 `rate_limit`，不再混进 `request_failed`）。`planner/pipeline.py:536-552` 的 `search_unavailable`/`route_unverified` 文案附原因（当前 `search_unavailable` 直接写「开放规则未核实」，丢了原因）。

## 14. 风险与取舍

1. **`day_window` 改造面大**：无 `rail_window` 时输出保持逐字不变，`evals/test_itinerary.py:1077` 的 pinned 断言是回归门。
2. **`travel_time` 可能长期停在 `reference`**：高德公交换乘接口本身支持 `date`/`time`，但拿到结果仍只标 `reference`——「有结果」不等于「已适用于规划日期与时段」；不粉饰、也不因无法核实就删掉这个 check。
3. **`must_visit` 收敛**会改变若干测试写法；业务上更严格（模型不能自行升级必去项）。
4. **`request_context` 新增于快照**：需处理 v3 旧快照；旧行程复用一律降级 unverified。
5. **`mode="confirm"` 是新请求字段**：旧客户端不传即按 `plan` 处理，保持兼容。
6. **不承诺线上验证**：离线通过只证明控制层与既定用例；`pytest -m integration` 与 `python -m evals.run_golden` 需用户授权且产生费用。
7. **`lodging_scope`/`party_size`/`budget_scope` 不写进 `TravelSlots`**：它们描述本次请求的确认状态，不是出行需求本身。
8. **中转工具暂不启用**：`get-interline-tickets` 在拿到真实样本前不解析；若将来返回结构变化，只需补样本与测试后加入 `TRAIN_RESULT_TOOLS`。
