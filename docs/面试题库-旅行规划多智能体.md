## 开场 30 秒（可整段背）

我做的这个旅行规划多智能体，解决的不是"能不能生成一份好看的行程"，而是三件在外部工具不可靠时特别容易崩的事：工具面怎么分、外部服务挂了怎么降级、成文阶段怎么拦住编造。我把地图和车票拆成两个子任务，各自只拿到自己那一组工具——地图只有校验过参数的 `amap_poi_search`，车票只有查询所需的 12306 工具，最后成文是一次没有工具的调用。这样拆分的目的不是多一段人设，而是让"地图写不了票、车票改不了技能包、成文不能临场再查"这三条成为结构事实，而不是提示词里的请求。第二层是降级：车票服务连不上、超时、或者根本没被调度，这几种状态是分开的，最终文本会照实说明，并且在没有可靠票务时禁止出现车次号。第三层是成文之后的闸门：检查六个固定章节在不在，票务不可靠时拒绝可识别的车次号，失败重试一次，还失败就换成固定降级文本。我要强调的是这三层都是**收窄**，不是解决——它保证的是"错了会被拦在落盘之前"，不是"模型不会犯错"。

# 一、项目定位与取舍

### Q1. 先简单介绍一下这个项目：它到底做什么、为什么值得做？

**在考什么**：你能否在三十秒内把问题定义讲清楚，而不是从技术栈开始念。

**口述版**：输入是一句中文旅行需求，比如"这周六从新乡坐高铁去郑州一日游，预算五百，少折腾"，输出是一份六章节的行程方案，加一张路线地图，加车票建议。这个场景看着简单，但它把 Agent 应用最容易翻车的三件事同时摆出来了：第一，能力是靠外部服务给的，高德和 12306 都不是我控制的，随时会挂；第二，钱和真实信息绑在一起，编一个车次号比编一段文案严重得多；第三，一次规划是分钟级的、要跑很多轮工具调用，成本和时延都不能假装不存在。所以我没有做"更聪明的行程推荐"，而是把力气花在三个可控性上：工具面按职责切开、外部失败有明确状态和降级路径、成文之后有一道能说清边界的闸门。它是个个人项目，不是产品，我把它定位成"可演示、可讲清设计边界"的作品。

**证据**：入口 `server.py` / `app.py`，核心在 `planner/pipeline.py` 的 `stream_plan`；六章节定义在 `planner/summary.py`。

---

### Q2. 你为什么要拆成多个子智能体？一个 Agent 拿着全部工具不是更简单吗？

**在考什么**：你拆分是为了职责边界，还是为了"看起来像多智能体"。

**口述版**：一个 Agent 拿全部工具的代价不是代码复杂，是**能力边界说不清**。如果地图子智能体也能调 12306、车票子智能体也能改技能包、成文阶段还能再查一次，那我没有任何一处能指着说"这里不可能发生某件事"，所有边界都退化成提示词里的请求，模型换个说法就可能不遵守。拆开之后边界变成结构事实：车票那个子智能体根本没有任何文件工具，所以它改不了技能包不是因为它听话，是因为那条路径不存在；成文是一次不带工具的调用，所以它不可能在成文阶段再查票。我付出的代价是调度层变复杂——要按路由结果决定挂哪几个子智能体、要处理子智能体结果怎么回收——但换来的是每条边界都能被单独测试和单独解释，这个交换我觉得值。

**证据**：子智能体定义在 `planner/map_agent.py`、`planner/ticket_agent.py`；挂载逻辑在 `pipeline.py`；决策记录见 `docs/adr/0004-subagent-is-tool-surface.md`。

---

### Q3. 这个项目的技术选择里，你最不后悔的一个和最想重做的一个分别是什么？

**在考什么**：你有没有真实的取舍判断，还是只会讲做成了什么。

**口述版**：最不后悔的是把路由做成纯规则函数。要不要连 12306、要不要跑地图，这两个决定会花钱、会打外部服务，交给模型的话我没法在不付费的情况下断言"同一句话永远走同一条路"，也就没法做离线回归。做成规则之后，每条用例的查票和出图决定都能在单测里锁死，代价是新说法要加关键词、不会自动泛化，这个代价我认。最想重做的是成文闸门的检查方式：它现在是子串匹配，六个章节词只要在正文里出现过就算通过，实际上不保证它们是六个二级标题；车次检查也只扫"车票建议"那一节。这两点在做的时候是为了快速拿到一个能挡编造的护栏，但事后看，它给出的保证比名字听起来弱。

**证据**：路由 `planner/routing.py`；闸门 `planner/summary.py::summary_gate_issues` + `evals/checkers.py`。缺陷验证见 Q13-2、Q13-3。

# 二、工具面隔离与权限

### Q4. 三个智能体各拿到什么工具？这条线你是怎么划的？

**在考什么**：你能不能说出"谁能做什么"的清单，而不是笼统说"做了权限隔离"。

**口述版**：地图子任务只有 `amap_poi_search`。路线、排程和地图 HTML 由编排层写，不把 shell 交给模型。车票子任务只拿到查询所需的 12306 工具，连接按这次请求创建和关闭。成文是编排层的一次无工具调用。所以"三个智能体"要拆开听：地图和车票是限工具的子任务，成文不是。

**证据**：`planner/backends.py` 的 `CompositeBackend` 与 `ReadOnlyBackend`；`map_agent.py` 与 `ticket_agent.py` 的配置；`summary.py::stream_summary`。

---

### Q5. "只读挂载"具体挡住了什么？它是不是就等于一个沙箱？

**在考什么**：你会不会把一个文件层的限制说成安全隔离。

**口述版**：挡住的是文件 API 的写操作：改、删、上传，这四类在那条路径上被直接拒绝，返回值是错误而不是靠模型自觉。它不是沙箱，这个界线我会主动说清楚：技能包是只读挂载的，但子进程是在宿主机上跑的，shell 仍然能执行命令、仍然能读磁盘上的文件、也仍然能出网。我另外做了一件独立的事，是把子进程的环境变量白名单化——不继承父进程环境，只放行启动 node 必需的那几个变量外加高德 Key，所以密钥不会通过环境变量漏进子进程。但这两件事各管一层，合起来也不构成沙箱：真要挡住文件和网络，得换到容器里执行，而不是在 Python 里再包一层。我把这两条未缓解的缺口写进了决策记录的风险矩阵，没有掩饰。

**证据**：`backends.py::ReadOnlyBackend`（write/edit/delete/upload_files 四件套）；`backends.py::shell_env` 的 `inherit_env=False`；风险矩阵见 `docs/adr/0003-shell-boundary.md`。测试：`evals/test_gate.py::test_skill_route_rejects_writes`、`::test_shell_env_hides_llm_key`。

---

### Q6. 密钥白名单是怎么做的？你能保证模型读不到密钥吗？

**在考什么**：你分不分得清"切断一条路径"和"保证做不到"。

**口述版**：做法是子进程完全不继承父进程环境，只显式放行启动 node 需要的几个系统变量，再加一个高德 Key。所以模型在子进程里读环境变量取不到大模型的密钥，这条路被切断了。但我只能说这条路被切断，不能说"模型读不到密钥"——磁盘上的配置文件它仍然读得到，因为它有可执行的 shell，而 shell 没有被限制在工作目录里。这是我这个设计里明确的已知缺口，写进了风险矩阵的"未缓解"那一栏。要真正解决只有两条路：要么把执行放进容器并挂载最小可见的文件系统，要么把 shell 能力本身收掉、改成预先定义好的有限命令集。这两条在当前形态下都属于重构，我没有做。

**证据**：`backends.py::shell_env` 的 `_SHELL_KEEP`；`test_shell_env_hides_llm_key` 同时断言函数返回值和真实 backend 的环境。

---

### Q7. 车票子智能体为什么干脆不给它文件工具？它要是需要写个缓存怎么办？

**在考什么**：你是从威胁模型划的线，还是从"这个 agent 需要什么"划的线。

**口述版**：因为车票这个职责里没有任何一步需要写文件，它只需要调工具、把结果返回给主智能体。给了文件工具就等于凭空多出一条"它能改东西"的路径，而这条路径的业务价值是零，风险不是零。至于缓存，它不在车票子智能体里做，而是在编排层做：编排层负责维护连接和结果复用，子智能体只是一个被调用的工具面。这个划分的好处是缓存策略、超时、重试这些横切关注点都留在我能测试的地方，而不是塞进一个跑在模型循环里的智能体。代价是车票子智能体每次都要靠返回值沟通，不能自己落盘积累状态——但这个项目里本来也不需要它积累。

**证据**：`ticket_agent.py` 只挂 MCP 工具；缓存与失败冷却在 `planner/ticket_cache.py`。

### Q8. 你怎么证明这些边界不是"只在提示词里写了要求"？

**在考什么**：你会不会把提示词约束当成机制。

**口述版**：靠三样东西。第一，隔离发生在工具装配层而不是提示词层：哪些工具挂给哪个子智能体是配置出来的，不是让模型别调用；只读也是后端层的拦截，写操作返回错误。第二，有测试直接断言后端行为，比如往技能包路径写、改、删、上传，四类操作都断言返回错误，而不是断言模型说了什么。第三，降级路径也是配置驱动的：连不上就不挂载那个子智能体，而不是挂上了再要求模型别用。我要说清的边界是：我证明的是"结构上那条路不存在"，不是"模型不会试图走那条路"。这两件事在面试里经常被混着问，其实是两回事。

**证据**：`test_gate.py::test_skill_route_rejects_writes`；`test_stream_plan.py::test_stream_plan_driving_skips_ticket_step` 断言自驾场景车票子智能体根本没被装配。

**追问 Q8-1：那"地图智能体没有车票工具""成文没有工具""结果目录可写"这三条，你有测试吗？**

**口述版**：没有，这三条我如实说。现有测试能证明的是技能包路径拒绝写、以及自驾场景下车票子智能体没有被装配；"地图那侧的工具清单里不含车票工具""成文那次调用没有工具""结果目录确实可写"这三条，在我核对过的测试里没有对应断言，它们目前只是代码结构上的事实，不是我拿测试钉住的。这是我这套测试的一个真实缺口，我要在面试里说清楚，而不是等被翻代码。

**证据**：`evals/test_gate.py`、`evals/test_stream_plan.py` 全量核对后无对应断言。

# 三、外部依赖与降级

### Q9. 车票服务连不上的时候，你的系统会怎样？

**在考什么**：你是"整个流程失败"，还是有明确的降级路径。

**口述版**：连不上就降级，而且是分层的降级。连接层有多长时间超时、失败之后有一小段冷却窗口不再反复重连，这些都在编排层控制，不在模型手里。如果最终拿不到工具，车票这个子智能体就不挂载了，主智能体只在没有车票工具的情况下调度地图。成文的时候，票务状态会被显式写进约束段落，模型被要求在这一节里说明服务不可用，并且禁止出现车次号。最后落盘之前还有一道闸门复查车次号。所以端到端的行为是：方案照常生成，车票那一节明确写"服务不可用、暂无可靠票务数据"，不会编一个车次糊过去。代价是这一节的信息量确实低，用户得自己去查。

**证据**：`planner/ticket_agent.py`（超时与重试次数）、`planner/ticket_cache.py`（冷却窗口）、`planner/summary.py::ticket_summary_block`（按状态生成约束文案）。

---

### Q10. 票务状态你一共分几种？为什么要分这么细？

**在考什么**：你的状态设计是按失败模式来的，还是随手加了个布尔值。

**口述版**：分六种，而且这个数字我要主动纠正：项目文档里有些地方还写着"五态"，实际有六种。分别是成功、无需铁路而跳过、服务不可用、本应调度却漏了、超时，以及修订时沿用上一版票务。分成六种不是为了好看，是因为它们对应的处理方式完全不同：无需铁路要去掉"服务故障"的暗示，服务不可用要照实说明，漏调度说明是我的编排出了问题、要额外告警，超时要说明是等待问题。如果只有"成功/失败"两态，自驾场景就会被写成"车票服务故障"，那是对用户撒谎。六种里有一个优先级顺序是硬约束、不能改：跳过必须排在服务不可用之前，否则同城和自驾这类本来就不需要铁路的情况，会被误报成外部服务挂了。

**证据**：`planner/routing.py` 的 `TicketState` 与 `resolve_ticket_state`；顺序约束写在 `evals/cases.md`；测试 `test_routing.py::test_resolve_ticket_state_priority`。

### Q11. 你说有"超时"这个状态，你验证过真实超时吗？

**在考什么**：你会不会把纯函数层的验证说成端到端验证。

**口述版**：只在纯函数层验证过，端到端基本不可达，这个我要说清楚。原因是当一个规划需要地图时，调度层是故意不设总超时的——地图子智能体是整个流程里最长的一段，如果给它设超时，就会在它写地图文件的中途把生成器关掉，地图直接残掉。所以真实规划里那个超时分支几乎没有机会触发，我只有把参数 mock 出来才能构造出来。被问"你验证过超时吗"，我的答案是"状态机层面验证过、真实链路没有"。这也解释了为什么这个状态在真实跑批里我从没观察到一个实例。

**证据**：`pipeline.py` 中 `timeout_seconds=None if need_map`；`test_routing.py` 的纯函数断言；`test_stream_plan.py` 用 mock 构造超时。

### Q12. 车票工具缓存是怎么做的？为什么一次完整规划基本命中不了？

**在考什么**：你知不知道自己的优化在真实工作负载下有没有用。

**口述版**：缓存是进程内的，成功之后保留五分钟，失败之后有一小段冷却不再重连，并且用一把锁把握手串行化，避免并发请求各建一个连接、互相覆盖泄漏。听起来合理，但真实情况是一次跨城规划本身远长于五分钟的存活窗口，所以完整的第二次规划根本命中不了；命中只会发生在同一个进程里、五分钟之内的第二次握手，比如评测脚本连续跑同一场景。我实测过冷启动握手和热命中的差别，热的那次接近零。所以这个缓存的实际收益主要在评测和调试，不在生产工作负载，这一点我会说清楚，不会把它包装成一个明显的性能优化。

**证据**：`planner/ticket_cache.py` 按请求创建和关闭连接，不再做进程内 TTL 缓存。

# 四、成文闸门

### Q13. 成文的闸门到底检查了什么？

**在考什么**：你能不能说清一道护栏的真实覆盖范围。

**口述版**：检查两件事。第一，六个固定章节在正文里都出现过：需求摘要、景点建议、车票建议、预算、行程表、注意事项。第二，当票务状态不是"成功"也不是"沿用上一版"时，"车票建议"这一节里不允许出现可识别的车次号，识别规则是常见车次前缀加三到四位数字。不通过就带着失败原因重试一次，第二次还不过就整段换成一份固定降级文本，那份降级文本自己也必须过闸门。它明确**不**检查的：景点是否真实存在、里程票价是否合理、预算是否算得对、行程安排是否可行。所以它是出口处的一道窄闸，不是事实校验器。

**证据**：`planner/ticket_facts.py`、`planner/summary.py::summary_gate_issues`；`evals/test_quality.py::test_g1234_in_summary_is_removed_when_raw_lacks_it`。

**追问 Q13-1：为什么不重试三次、五次，而只重试一次？**

**口述版**：因为重试的收益在第一次之后掉得很快。第一次失败通常是结构和约束没被遵守，比如漏了一个章节、或者在禁止写车次的地方写了车次，把具体失败原因回填到提示里再让它改一次，命中率是有的。第二次还不过，说明问题不在"它没注意到"，而在"它拿不到足够的信息"或者"这个模型当前就是做不到"，这时候继续重试只是把同一段失败重复几遍，白花钱、白等时间，还会让用户在已经等了很久之后再等一轮。所以我选的是快速给一个诚实的降级文本：六个章节齐全、明确说明本次校验没过、不编细节。降级文本本身也要过闸门，这样至少保证"降级"不会变成"换个方式编造"。

**证据**：`pipeline.py` 的两次尝试循环；`degraded_plan` 的六章节结构。

**追问 Q13-2：章节检查是怎么实现的？会不会被绕过？**

**口述版**：会，而且这一点我实测过。实现是子串匹配，只要六个词在正文里都出现过就算通过，不要求它们是六个二级标题、也不要求顺序和结构。我实测把六个词平铺成一行、中间没有任何标题结构，检查依然返回通过。所以它验的是"这些词出现过"，不是"文档有那六个章节"。要真正钉住结构，得改成解析 Markdown 标题层级、按顺序比对标题文本，这是我知道该改但还没改的地方。面试里我会主动说这条，因为它决定了这道闸门的保证有多强。

**证据**：`evals/checkers.py::has_required_sections` 用的是 `all(section in body)`；复现：`has_required_sections("需求摘要 景点建议 车票建议 预算 行程表 注意事项")` 返回 `True`。

**追问 Q13-3：车次号检查会不会漏？**

**口述版**：会，有三个漏点。第一，它只扫"车票建议"这一节，把车次写进"行程表"或者"注意事项"就不会被拦，我实测过这种情况闸门返回空、直接放行。第二，当票务状态是"成功"时它整段跳过车次检查，所以成功态下的编造车次没有任何人管。第三，正则本身只认常见的那几个车次前缀加三到四位数字，四位数以上或者非常规前缀会漏。这三条合起来说明它是一道窄闸：它主要防的是"票务明显不可靠时还硬写一个典型车次号"，而不是"车次号一定正确"。我把它定位成成本很低的兜底，而不是正确性保证。

**证据**：`checkers.py::assert_no_fabricated_trains` 只取"车票建议"章节；`summary.py` 中 `ticket_reason in ("ok","reused")` 时跳过检查；复现：把车次写进"行程表"，`summary_gate_issues` 返回 `[]`。

### Q14. 你让模型自己检查一遍输出，不是更省事吗？为什么非要做一个硬闸门？

**在考什么**：你懂不懂"让模型检查自己"的循环论证。

**口述版**：因为自评和生成是同一次调用、同一个上下文，生成的时候它已经认为这样写是对的，检查的时候大概率给出同样的判断，等于把同一个错误确认了两遍，还多了一道看起来很正规的步骤。而且自评的结论是一句主观的话，人没法拿"模型说它对"去跟业务对质。硬闸门不一样，它是拿规则比字符串，谁跑、什么温度、换哪个模型，结果都是稳定的，还能写成测试卡住回归。同样的理由也用在票务状态上：我不拿模型的置信度当门槛，状态由工具有没有返回、有没有挂载这些可观察的事实决定，不由模型说。

**证据**：`summary_gate_issues` 是纯函数；`resolve_ticket_state` 只看四个布尔事实。

# 五、路由与澄清

### Q15. 为什么"要不要查票、要不要出地图"用规则算，不交给模型？

**在考什么**：你是为了可测还是为了省 token——以及你知不知道这个选择的代价。

**口述版**：因为这两个决定的后果是钱和外部副作用。连 12306 要握手、要等待、可能失败；跑地图是整次规划里最贵的一段，多轮工具调用。交给模型的话，我没法在不花钱的情况下断言"同一句需求永远走同一条路"，也就没有稳定的离线回归。做成纯函数之后，每条用例的查票决定和出图决定都能在单测里钉死，不受模型版本影响。代价很清楚：新说法要加关键词，不会自动泛化。比如用户说"坐大巴"，关键词表里没有，系统仍然会去查火车票；用户说"不坐高铁"，否定式没有被特别处理，也仍然会查。这些是我知道的实际短板，我选择用"加关键词 + 补用例"的方式维护，而不是退回给模型判断。

**证据**：`planner/routing.py::skip_ticket_reason` / `skip_map_reason`；用例表 `evals/cases.md` 与 `evals/test_routing.py` 顶部 `CASES` 同构，共 6 条。

**追问 Q15-1：那"同城"这个分支你测过吗？**

**口述版**：没有，这是个真实的缺口，我核对时才发现。测试里有一条用例名叫同城，但那条查询里带着"自驾、不坐火车"这样的交通词，所以它实际命中的是"无需铁路意图"这个更靠前的分支，真正靠同城判断走的那条路没有被任何用例覆盖。我实测过同城、不带交通词的输入确实会走到同城分支，所以功能是通的，只是没有测试守着它。这类"名字对但覆盖的不是那个分支"的用例，比完全没有用例更危险，因为它会让人误以为覆盖过了。

**证据**：`evals/test_routing.py` 的 `CASES` 中 intra_city 用例查询含"自驾、不坐火车"；实测同城无交通词返回 intra_city。

### Q16. 什么情况下系统会停下来问用户，而不是自己猜？

**在考什么**：你的澄清条件是设计出来的，还是遇到问题随手加的。

**口述版**：两类情况会停。第一类是出发地、目的地、出行日期这三项缺任何一个，因为这三项缺了之后后面所有判断都失去依据，猜出来的一定是错的。第二类是多日行程没说住哪儿——这一条是后来加的，因为多日行程如果不知道住宿地，每天的路线起点终点都编不出来，模型就会自己编一个酒店，而酒店编错了整条路线都是废的，所以宁可停下来问。除了这两类，其余的都往下走：预算、偏好、节奏这些有默认值，系统会填上并且标记哪些值是默认的。还有一条边界要说：如果槽位抽取这一步本身抛异常了，系统不会弹确认卡，而是退回用正则从原话里抓，或者退回一个不带结构化约束的老提示词，也就是说"缺字段一定问"只在抽取成功时成立。

**证据**：`slots.py::clarify_missing` / `should_clarify`；抽取失败的三级降级在 `pipeline.py`。

**追问 Q16-1：多日行程缺住宿地这条，有测试吗？**

**口述版**：没有直接测试，我如实说。现有测试断言的是"住宿地不算关键字段"这一面，也就是住宿地空着不会被算成关键字段缺失，但它没有断言"多日行程缺住宿地会触发澄清"这个反向行为。这个行为的证据目前只有一次端到端实跑记录，不在回归里。这是我该补但还没补的用例。

**证据**：`evals/test_unit.py::test_lodging_empty_is_none_and_not_critical` 只断言 `missing_critical` 不含住宿地；`clarify_missing` 全仓无直接断言。

# 六、增量修订与快照

### Q17. 用户说"不要龙门石窟了，改白马寺"，系统怎么处理？

**在考什么**：你是每次都重跑一遍，还是真的做了增量。

**口述版**：先分类这次修订动的是什么。如果动的是日期、出发地、目的地或者出行方式，那票务和地图都要重来；如果只动行程内容，比如换景点、调整顺序，那票务不需要重查，直接沿用上一版的票务结果；如果只是改措辞语气，那连地图都不用重跑，只重写成文。只改行程这条路径上，系统不会再抽一次槽位、也不会再连一次车票服务，这两个调用被跳过，是能测出来的。沿用的票务还有一个风险要处理：旧方案里的地图文件名是按旧标识命名的，直接复用会让新方案指向旧地图，所以沿用时要把标识替换掉，并且在成文里明确写"车票信息沿用上次查询"，不许当作新查的结果来陈述。

**证据**：`routing.py::classify_revision`；`pipeline.py` 修订分支；`test_stream_plan.py::test_map_only_revision_skips_extract_and_ticket`（断言抽槽位和连车票都没被调用）。

**追问 Q17-1：改了日期和出发地，但你的旧票务还留着，会不会串？**

**口述版**：不会串，因为"改四要素"这一类走的是重查路径，不沿用旧票务，并且成文时会额外加一条约束：上一版方案只用来保持结构一致，车票和票价一律不得沿用，必须以上一轮新查的结果为准。真正会沿用旧票务的只有"只改行程内容"和"只改措辞"这两类，而这两类的前提是四要素没变，所以旧票务在语义上仍然成立。这两条分支我只有分类函数的单测，没有端到端测试，这是我知道的一个覆盖缺口。

**证据**：`pipeline.py` 中 `revision_forbid_old_tickets`；`test_routing.py::test_classify_revision_four_factors` 只测分类。

---

### Q18. 你简历里写了"支持中断恢复"，这个能力到底存在吗？

**在考什么**：你敢不敢当场纠正自己材料里的表述。

**口述版**：不存在，这个说法我要主动纠正。项目里没有断点续跑：没有检查点存储、没有线程标识、没有那种"进程挂了以后从中间继续"的机制。澄清的实际实现是"这一轮直接结束、返回一个待确认事件，前端带上已确认信息重新提交一次、是一个全新的规划、新的方案标识、重新走理解那一步"。所以准确的说法是**增量修订**：我保存了上一版方案的上下文，用来让"改一版"这件事不必从头再来，但它不是运行态恢复。两者的区别很实际：修订是用户主动发起的、有完整上一版可依的；续跑是进程被打断之后自动接上，这个我没有做。快照的用途只有两个：修订时复用上下文，以及评测时取证。

**证据**：全仓无 `checkpointer` / `thread_id` / 会话保存器；`summary.py::save_snapshot` / `load_snapshot`；`pipeline.py` 澄清分支直接 `return`；`server.py` 前端带槽位重新请求。

**追问 Q18-1：那"两套存储"你打算怎么讲？**

**口述版**：我只有一套，就是快照文件，它保存的是给下一轮修订用的业务上下文，不是执行位置。所以我不讲"两套存储职责不同"，因为没有第二套。如果将来真要做续跑，快照本身可以复用为"业务内容"，但执行位置必须另有地方存，这两者职责确实不同——不过那是我打算做的设计，不是现在的实现，我不会把设想说成已有。

### Q19. 快照这块你处理过什么安全问题？

**在考什么**：你会不会因为"个人项目"就完全不想安全。

**口述版**：做过一件具体的事：方案标识只接受标准 UUID，不接受任意字符串，因为快照是按标识拼文件路径去读的，如果允许任意字符串，一个带路径穿越的标识就能读到项目外的文件。这条有测试，拿一个穿越字符串传进去，系统直接返回错误、不读盘。其余就没什么了，如实说：快照本身没有归属校验，也没有保留期限和清理任务，目录会一直涨——我本地已经积累了两百多份，靠手动清理。所以它是"堵了一个具体的洞"，不是"做了安全设计"。

**证据**：`summary.py::parse_plan_id` 的 UUID 白名单；`test_stream_plan.py::test_plan_id_path_traversal_rejected`；磁盘实测 219 份快照。

# 七、流式、取消与并行

### Q20. 为什么这个接口用流式推事件，而不是等跑完一次性返回？

**在考什么**：你知不知道流式在这里真正解决的是什么问题。

**口述版**：因为一次规划是分钟级的，那几十分钟里如果什么都不返回，用户完全不知道系统是在干活还是卡死了，也没有机会在中间判断要不要放弃。流式推的是**步骤状态**，不是模型的思考过程：理解需求、查票、出地图、成文这四步各自的开始、完成、跳过，跳过还要带原因。用户看到的是一条进度条，能看出"现在卡在地图"，而不是一个转圈的等待。我刻意没有把模型的中间输出实时流出去，因为它们随时会被覆盖，让人看到一份一直在变的清单，信任消耗比"多等一会儿"更贵。成文阶段是例外，它本身就是最终文本，所以是逐字流出来的。

**证据**：`server.py` 的 SSE 端点；事件类型表见 `README.md`；`planner/dispatch.py` 把调度过程翻译成步骤事件。

---

### Q21. 用户关掉页面的时候，正在跑的规划会怎样？

**在考什么**：你对"取消"的边界说得准不准。

**口述版**：会尽快停，但停的位置有边界。服务端会检测到连接断开，置一个取消标志，事件循环每半秒检查一次，一旦置位就把正在消费的异步生成器关掉，后续的模型调用不再启动。所以它的保证是"不再开始新的调用"，能省钱。它不能保证的是"已经发出的请求会回滚"——正在跑的那次模型调用、正在握手的那个外部服务，不会因为我关页面就撤回，只是我不再等它的结果。另外一个要说准的地方：取消对客户端是不可见的，因为流已经断了，没有"已取消"这个事件；服务端只是安静地结束这一轮。所以在服务端能区分的是调度超时、闸门降级和异常这三类，取消不在其中。

**证据**：`planner/async_utils.py::watch_aiter`（半秒轮询 + aclose）；`server.py` 的断开检测；`test_stream_plan.py::test_watch_aiter_cancelled_stops_clean`。

---

### Q22. 你的提示词要求"同一条消息里同时调度地图和车票"，你怎么证明它真的并行了？

**在考什么**：你会不会拿一个布尔值当结论。

**口述版**：我不看那个布尔值，因为它设计得有问题：它要求两个子智能体的结果落在同一次工具消息里，而车票很快就结束、地图要跑很久，结果必然分两次回来，所以这个布尔值几乎永远是假，即使真的并行了。我用的是三个量：两个子智能体各自被激活的时间戳之差，用来看它们是不是同一轮发出去的；调度总墙钟；以及"地图耗时加车票耗时"这个串行下界。前两个对比第三个，才能判断并行有没有换来时间。为了做对照，我还加了一个开关，能把提示词改成"先等地图再查票"，然后两种模式各跑五次。结论是：提示词能把开始时间拉开——开并行的五次里有四次两个子智能体同时开始，串行模式五次都拉开了；但总墙钟几乎没省，两种模式的中位数只差一分钟左右，小于单次之间的波动。所以我只能说"提示词能让它们同时开始"，不能说"并行带来了明显收益"。

**证据**：`planner/dispatch.py` 的时间戳与 `pipeline.py` 的耗时字段；对照数据 `evals/serial.json`；`test_gate.py::test_force_serial_changes_rail_prompt`。

**追问 Q22-1：五分钟的样本、一个场景，你的结论有多大可信度？**

**口述版**：只能当方向性观察，不能当普适结论，这个我会自己先说。样本是每种模式各五次、每次新进程、同一个场景，所以它压不住单次波动；而且这个项目的耗时主要在地图那一段，车票那几十秒本来就不是瓶颈，理论上并行能省的上限就很低。所以更准确的表述是"在这个场景下，并行没有可观测的墙钟收益，因为车票不是瓶颈"，而不是"并行没用"。要真下结论得换一个车票也是瓶颈的场景，那我没有做。

# 八、评测、成本与上生产

### Q23. 你怎么评测这个系统？评测分数能说明它很准吗？

**在考什么**：你会不会把回归测试说成模型效果。

**口述版**：先分两类。第一类是确定性回归，不调模型、不连外网，钉的是流程契约：该跳过的是不是真的跳过了、票务状态是不是按优先级算对了、闸门该拦的是不是真的拦住了、路径穿越是不是真的被拒了。这类测试的价值是防止"加一个改动把某条护栏悄悄拆掉"，因为那种回归最阴险——流程照样跑完，只是某道闸没了。第二类是真实跑批加模型打分，用来观察生成质量。这一类我必须交代偏差：打分用的模型和被评的模型是同一个，所以分数只能当对照，不能当独立评审，这个偏差我显式记在了产物文件的元数据里。另外那一批数字跑在一个已经改过的旧流水线上，报告里自己声明了不能当基线，所以我现在不会引用那些分数。

**证据**：`evals/` 下的确定性测试与 `run_golden.py` 跑批；`judge.py`；`judge_results.json` 里的同源标记；`EVALS.md` 的复核段。

**追问 Q23-1：那你能说多少个测试吗？**

**口述版**：能说两个不同的数字，而且要说清区别：收集到七十六项，其中进默认 CI 的是七十四项，另外两项要真实模型 Key、不进 CI。但"七十四项通过"这句话我不能说，因为我核对的那台机器上依赖没装全，实际执行全部报错，那是环境问题不是测试问题，但在没有自己跑出绿色之前，我只会说"这些测试存在并带有断言"，不会说"它们全绿"。这个区分在面试里很重要，把 collect 数量说成通过数量是很容易被抓的。

**证据**：`pytest --collect-only` 输出 76 项，`-m "not integration"` 74 项；`evals/conftest.py` 与缺失依赖导致执行期报错。

### Q24. 跑一次大概多少钱、多久？这个成本你怎么管？

**在考什么**：你对自己的东西有没有量化的感觉。

**口述版**：具体数字我不能给你，因为唯一那批实测跑在旧流水线上，代码已经改过（多了一条"多日行程缺住宿地要确认"的规则），那些数字不能代表现在。我能说的是结构：成本几乎全在地图子智能体那一段的多轮工具调用，最后那一次成文是单次调用、占比很小；所以真正要控成本得动地图那一侧的轮次和工具返回体积，而不是动成文。系统里做了 token 和成本的统计，统计方式是在每次调用的流式结尾取累计值、避免把同一个调用的多帧重复累加，这条有精确断言的单测。单价走环境变量，不写死厂商价目。但我不会拿这个统计去承诺"一次多少钱"，因为地图那一侧的轮次随需求变化很大。

**证据**：`planner/usage.py`（流式取最大值累加、单价走环境变量）；`test_gate.py::test_usage_counts_stream_total_once` 精确断言 token 与成本；`EVALS.md` 的成本段落与作废声明。

### Q25. 这套东西现在能上生产吗？还差什么？

**在考什么**：你心里有没有一张从演示到生产的距离清单。

**口述版**：不能，而且我要主动列出差在哪。第一是访问控制：结果目录是静态挂载、没有鉴权，知道文件名就能下载；健康检查接口也是公开的；快照里存着完整方案和槽位，没有归属校验。第二是限流：现在是单进程内存计数，多开一个工作进程就各算各的，挡不住打散到不同进程的请求；有一个可选的请求头密钥，但它的覆盖面很窄。第三是生命周期：方案、地图、快照都没有保留期限，也没有清理任务，目录只会涨。第四是没有删除接口，用户要求删数据这件事现在只能手工做。所以它现在的形态是一个单用户本地演示，不是多用户服务，我不会把它说成"基本能上生产只差压测"。

**证据**：`server.py`（静态挂载、限流、可选密钥）；`README.md` 的"已知边界"；`planner/plans_store.py` 的规划历史。

**追问 Q25-1：那个可选的请求头密钥，设了之后前端还能用吗？**

**口述版**：不能，这是一个我核对时发现的真实配置陷阱。前端发起规划请求时没有带这个请求头，所以一旦在环境变量里启用密钥，网页端会直接被拒，只有命令行或者自己写脚本带头才能用。也就是说这个密钥目前只对非浏览器调用者有意义，它不是一个完整的访问控制方案。要修的话前端得从某个地方拿到密钥再带上，但那又等于把密钥暴露在浏览器里，所以正确做法是改成服务端会话或反向代理层的鉴权，而不是加一个请求头。这一点我会在讲"可选密钥"的时候主动说清楚。

**证据**：`frontend/app.js` 的请求只设了 `Content-Type`；`server.py::_reject_bad_api_key`。

# 附一：表达风险清单（面试前必看）

**一、绝对不要说"支持中断恢复"。** 这个项目没有断点续跑，没有检查点存储、没有线程标识。澄清的实现是"结束这一轮、前端带已确认信息重新提交、新起一次规划"。正确说法是**增量修订**：保存上一版上下文，让"改一版"不必从头再来。被问到就说 Q18，顺带把"续跑"和"修订"的区别讲清楚，这是加分点。

**二、不要再说"票务五态"。** 是六态，多出来的是修订时沿用上一版。项目里有些文档还写着五态，你自己讲的时候要按六态说，并且可以主动指出"我们文档还有地方没同步"——这比被抓住强。

**三、三道护栏的强度不要夸大，这三条我都实测过。** ①章节检查是子串匹配，六个词平铺成一行也会通过；②车次闸门只扫"车票建议"一节，写进"行程表"不拦；③票务成功时整段跳过车次检查。所以它该被描述成"成本很低的窄闸"，不是"事实校验器"。答法见 Q13-2、Q13-3。

**四、"只读挂载"不等于沙箱。** 挡住的是文件 API 的写操作；shell 仍能执行命令、读磁盘、出网。可以说的只有环境变量白名单切断了密钥继承这一条路径，不能说"模型读不到密钥"。答法见 Q5、Q6。

**五、测试数字只说"存在"，不说"全绿"。** 收集 76 项、进 CI 74 项，但你没有自己跑出绿色记录，就不要说"74 项通过"。答法见 Q23-1。

**六、耗时、token、成本、judge 分数一律不引用。** 那批数字来自一个已经改过的旧流水线，报告自己声明作废；打分模型与被评模型同源，分数不是独立评审。被问就说结构、说"哪一侧占大头"，不说具体数值。答法见 Q23、Q24。

**七、别把"票务超时"讲成验证过的能力。** 它只在纯函数层验证过，真实链路里因为"需要地图时不设总超时"而几乎不可达。答法见 Q11。
