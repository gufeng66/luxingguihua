# 旅行规划多智能体：动手练习与证据锚点

> **这份不是面试问答。** 面试口述稿在 [面试题库-旅行规划多智能体.md](面试题库-旅行规划多智能体.md)——那份是"你嘴上要说什么"，这份是"你手上要做什么"。

面向 Agent 应用开发岗的自测练习卷。每题先自己实现，再用验收条件自测；每题末尾的「证据锚点」标出本仓库的对应实现和测试，以及**能证明到哪一步**。

用法：练习 → 对照锚点 → 复盘时把结论归入文末四类。不要求背整段口述答案；本文件不承担面试口述功能，叙述稿见题库那份。

## 阅读约定

**三个状态标签**，每题都会标：

| 标签 | 含义 |
|------|------|
| `本仓库无对应实现` | 题目是通用能力热身，仓库里没有可比对的代码 |
| `已实现·有测试` | 有代码、有确定性测试，可以指着测试名讲 |
| `已实现·证据有限` | 有代码，但测试只覆盖部分路径，或没有对照组 |

**术语统一到代码用词**，首次出现给中英对照：

| 中文 | 代码用词 | 出处 |
|------|----------|------|
| 槽位 | `TravelSlots`，critical = 出发地/目的地/日期，多日行程另加住宿地 | `slots.py` |
| 澄清 | `clarify`（`missing` / `defaults_applied`） | `slots.py::clarify_missing` |
| 路由 | `skip_ticket_reason` / `skip_map_reason`（纯函数） | `planner/routing.py` |
| 票务态 | `TicketState`：`ok` / `skipped` / `unavailable` / `missed` / `timeout` / **`reused`** | `planner/routing.py` |
| 地图态 | `MapState`：`ok` / `skipped` / `missed` / `timeout` / `incomplete` | `planner/routing.py` |
| 漏调度 | `missed`（本应调度但没发 task） | `planner/pipeline.py` |
| 成文 | `stream_summary`（无工具的一次 LLM 调用） | `planner/summary.py` |
| 闸门 | `summary_gate_issues`，结果 `pass` / `retry_pass` / `degraded` | `planner/summary.py` |
| 快照 | `snapshot`，修订用的上一版上下文存档，**不是 checkpoint** | `planner/summary.py` |

**票务是六态。** `ok / skipped / unavailable / missed / timeout / reused`；`reused` 由修订分支赋值，`resolve_ticket_state()` 本身不返回它。当前 README 与架构文档已按六态同步，回答时不要引用历史“五态”表述。

**数字与时效约定**：本文件不写耗时、token、成本、评分数字。引用任何数字时必须同时给出运行日期与代码版本；`docs/interview.md` 与 `EVALS.md` 表格里的数字来自 2026-10-07 的旧流水线，`EVALS.md`「复核（2026-10-12）」一节已声明作废，当前只能当量级参考。

**当前证据边界**（2026-11-14）：`travel-planner` Python 3.11.16 的未提交工作区离线回归为 `501 passed, 2 deselected`，但尚未绑定 commit SHA；CI 3.11/3.12、真实浏览器与真实外部服务均未验收。面试时可以说“控制层离线回归通过”，不能说“整体已上线验收”。

## 第一部分 · 重写热身（本仓库无对应实现）

### 1. 搭一个最小 ReAct Agent

实现一个命令行 Agent，提供两个本地工具，例如计算器和静态景点查询。模型可以按 `Thought → Action → Observation` 循环调用工具，最后输出 `Final`。

验收条件：

- 只能调用预先注册的工具，不能执行模型生成的任意 Python 或 shell。
- 工具参数按 JSON 解析；未知工具名和无效参数会得到明确错误。
- 设置最大循环次数；达到上限后停止并说明原因。
- 加测试覆盖一次工具调用、直接回答、无效工具名和循环超限。

> **证据锚点**：`本仓库无对应实现`。手写 ReAct 循环是**重写**，不是比对。练这题的意义是理解 `astream` 里 chunk 的形状——可以对照 `planner/subruns.py::bounded_loop` 怎么在有界循环里处理 tool_calls。
>
> **别照抄旧说法**：本项目历史上用过 DeepAgents 的 `create_deep_agent`，但**当前主路径不调用它**——`planner_service.py` 只在 deepagents 已安装时导入该符号（供历史模块与测试替换），真实规划由 `stream_plan` + `iter_agents` + `bounded_loop` 组合完成。回答「本项目用 create_deep_agent 编排」属于把历史实现当成当前能力。


### 2. 抽取旅行槽位并询问缺失信息

输入一句旅行需求，抽取出发地、目的地、日期、天数、预算和偏好。必需字段缺失时返回澄清问题，不要让 Agent 自己猜出发地或日期。

验收条件：

- 槽位使用固定结构，日期和天数有基本校验。
- 缺必需字段时返回 `clarify`，字段齐全时才继续。
- 软字段可以有默认值，但要标记哪些值是默认的。
- 用纯函数测试缺字段、完整输入和非法日期。

> **证据锚点**：`已实现·有测试`。`slots.py::clarify_missing` / `should_clarify`；critical 只有出发地/目的地/日期（`slots.py::missing_critical`），但**多日行程缺住宿地也会弹卡**（`slots.py::clarify_missing` 追加 `lodging`）；软字段默认值来自 `SOFT_DEFAULTS` + `apply_soft_defaults`，被填的字段名通过 `_clarify_event` 的 `defaults_applied` 回传前端。
>
> 测试：`evals/test_unit.py::test_critical_missing_triggers_clarify`、`::test_client_slots_complete_no_reclarify`、`::test_client_slots_still_missing_critical_clarifies`、`::test_soft_missing_does_not_block`、`::test_missing_critical_only_origin_dest_date`、`::test_travel_slots_rejects_bad_date`、`::test_travel_slots_rejects_non_positive_days`。
>
> **两处别说过头**：①「多日行程缺住宿地要弹卡」这条**没有单测**——`clarify_missing` 全仓没有直接断言，现有测试只断言 `missing_critical` 不含 `lodging`，实测证据只有 `EVALS.md` 里的一次端到端跑批。②相对日期解析有测试（`明天` / `下周六` / ISO 直通），但 `大后天` / `本周X` / `下下周六` 只有实现没有断言。
>
> **第三处**：`defaults_applied` 只有实现、没有断言。另外抽取**抛异常时不会弹澄清卡**，走正则兜底或 legacy 提示词（`pipeline.py`），即「缺字段一定问」只在抽取成功时成立。

### 3. 写一个确定性路由器

根据用户原话和已确认槽位，决定是否查票、是否生成地图。先实现同城游、自驾和跨城铁路三种情况。

验收条件：

- 相同输入总是得到相同路由结果。
- 路由只使用本次需求和已确认槽位，不读取长期画像来决定是否调用外部工具。
- 为每个跳过动作返回可解释的原因，例如 `no_rail_intent`。
- 不确定或未覆盖的说法有测试，也能说明规则路由的适用边界。

> **证据锚点**：`已实现·有测试`。`planner/routing.py::skip_ticket_reason` / `skip_map_reason` / `is_same_city`，纯函数不联网。`no_rail_intent` 之外还有 `intra_city`、`user_no_map`、`route_no_rail` 等（见 `pipeline.py` 各 `step` 事件的 `reason`）。
>
> 测试：`evals/test_routing.py` 顶部 `CASES` 与 [`evals/cases.md`](../evals/cases.md) 同构，6 条用例逐条断言 `need_ticket`；另测同城归一化、`新乡` vs `新乡县` 不算同城。
>
> **边界要说准**：修订分支会把**上一轮原话**也拼进路由输入（`pipeline.py` 中 `route_query = f"{snapshot['query']} {query}"`），所以严格讲不是「只看本次需求」。单轮规划时才是。
>
> 另外两条实测出来的洞：①`intra_city`（同城无交通词）分支**没有任何测试用例**——测试里叫 `intra_city` 的那条查询是「杭州自驾逛西湖，不坐火车」，实际命中的是 `no_rail_intent`；②否定式没处理，「不坐高铁」仍然返回 `None`（照样查票），「坐大巴」也不在关键词表里。这两条正好说明规则路由的适用边界。

## 第二部分 · 核心能力题

### 4. 给 Agent 划分工具权限

把地图查询和车票查询拆成两个工具组，再添加一个不带工具的汇总步骤。比较「一个 Agent 持有全部工具」和「按工具组拆分」两种设计的能力边界。

验收条件：

- 地图 Agent 不能调用车票工具；车票 Agent 没有任何文件工具，改不了高德 Skill 源文件；汇总步骤不能调用工具。地图 Agent 仍可把生成的地图产物写入允许的结果目录。
- 用配置或测试验证工具清单，而不是只在提示词里要求模型不要调用。
- 不把工具清单说成进程级沙箱；解释命令执行和文件只读限制各自覆盖什么。

> **证据锚点**：`已实现·有测试`。地图工具名单是 `amap_poi_search`，票务从 MCP 发现结果里按 `TICKET_QUERY_TOOLS` 挑选，成文 `stream_summary` 无工具。见 `planner/subruns.py`、`planner/ticket_facts.py`、ADR-4。
>
> 测试：`evals/test_quality.py::test_tool_allowlist_is_exact`；`evals/test_stream_plan.py` 断言自驾时不挂票务。
>
> **别说过头**：工具名单不是进程沙箱。当前规划路径不把 shell 交给模型。ADR-3 记录的是旧 shell 实现，不要把它讲成现在的地图步骤。
>
> **测试没盖住的三条**：「地图 Agent 没有车票工具」「`stream_summary` 没有工具」「`/workspace/results` 可写」都**没有断言**。现有测试能证明的是 skill 目录拒绝写、自驾时 `ticket_agent` 不挂载。另外 `summary_agent` 在 `dispatch.py` 里是个映射残留，实际成文走 `stream_summary`，别把它讲成一个真实挂载的子智能体。

### 5. 模拟外部工具故障并降级

用一个可控的 mock 车票工具模拟成功、超时和不可用。让规划流程在查不到票时继续生成方案。

验收条件：

- 票务状态能区分 `ok` / `skipped` / `unavailable` / `missed` / `timeout`，以及修订复用的 `reused`；优先级不可改序。
- 票务不可用时，最终文本明确说明原因，不生成车次号。
- 失败不会让地图规划和其他不依赖票务的步骤一起失败。
- 测试注入故障，验证状态和最终输出。

> **证据锚点**：`已实现·有测试`。`planner/routing.py::resolve_ticket_state` 的优先级固定为 `ok > skipped > unavailable > timeout > missed`；为什么 `skipped` 必须排在 `unavailable` 之前有明确理由——否则自驾/同城会被写成「车票服务故障」（见 `evals/cases.md`）。`reused` 在 `pipeline.py` 修订分支单独赋值。
>
> 测试：`evals/test_routing.py::test_resolve_ticket_state_priority`（逐级断言）、`evals/test_unit.py::test_resolve_ticket_state_five_state`、`evals/test_unit.py::test_ticket_summary_block_skipped_not_unavailable`、`evals/test_stream_plan.py::test_stream_plan_missed_ticket_warning`。
>
> 当前票务 MCP 连接按请求创建和关闭，不使用进程级 TTL 连接缓存。修订复用的是票务事实与其原查询时间，不是复用活跃 MCP 连接。
>
> **`timeout` 这条要说清楚**：它只在纯函数层被测到。端到端几乎不可达——需要地图时 `iter_dispatch` 的 `timeout_seconds` 传的是 `None`（要等 map 写完），所以真实规划里 `timeout` 基本只能靠 mock 构造。被追问「你验证过超时吗」，答案是「纯函数验证过、端到端没有」。

### 6. 给模型输出加一道窄而明确的闸门

检查汇总文本是否包含要求的章节；当票务不可靠时，拒绝车票章节中可识别的车次号。失败后重试一次，仍失败则返回固定降级文本。

验收条件：

- 测试正常文本、缺章节、无票却出现车次号和重试仍失败。
- 能说清这道闸门检查了什么、没有检查什么。
- 不把「没有可识别车次号」扩大成「预算、景点、路线等所有事实都已验证」。
- 进阶：从工具原文提取允许出现的实体，测试输出与来源是否一致。

> **证据锚点**：`已实现·有测试`。`planner/summary.py::summary_gate_issues`：六章节必须齐（`evals/checkers.py::missing_sections`）；票务不在 `ok` / `reused` 时，**只扫「车票建议」这一节**，正则是 `[GDCKT]\d{3,4}`（`evals/checkers.py::TRAIN_NUMBER_RE`）。失败带反馈重试一次，再失败用 `degraded_plan` 替换正文。
>
> 测试：`evals/test_quality.py::test_g1234_in_summary_is_removed_when_raw_lacks_it`（原文没有的车次不进最终方案）、`evals/test_gate.py::test_fabricated_train_is_retried_then_dropped`、`::test_valid_summary_is_not_retried`。
>
> **必须主动交代的三条**：①没有「关掉闸门」的对照组，只证明护栏生效，不证明编造率下降多少；②闸门只管车次号和章节，不管景点、里程、预算是否真实——真跑时低分案例正是「地图上下文只剩 HTML 路径，模型仍写出景点和过路费」（见 `EVALS.md`）；③正则只认 `G/D/C/K/T + 3~4 位`，`G12345` 或非字母前缀会漏。
>
> **三条实测出来的漏洞，被追问时不要嘴硬**：
> - 章节检查是**子串匹配**，把六个词平铺成一行也算通过（我实测 `has_required_sections("需求摘要 景点建议 …")` 返回 `True`）。所以它验的是「词出现过」，不是「有这六个 Markdown 二级标题」。
> - 车次闸门**只扫「车票建议」一节**。把 `G1234` 写进「行程表」不会被拦（实测 `summary_gate_issues` 返回空）。
> - 票务态是 `ok` 时**整段跳过车次检查**，所以 `ok` 场景下的编造车次无人管。
>
> 还有两处：`summary_gate=retry_pass` 没有测试覆盖；进阶要求里的「从工具原文提取允许实体做一致性校验」**没有实现**，`assert_ticket_section_consistent` 写好了但全仓没有调用点。

### 7. 把一次规划变成可取消的事件流

把规划过程改成逐步输出状态事件和最终结果。客户端断开时停止尚未开始的后续模型调用。

验收条件：

- 事件包含步骤状态、最终结果和错误信息，字段格式稳定。
- 超时、取消和普通失败能区分。
- 测试确认取消后不再启动后续调用；不声称已发出的外部请求一定能立即回滚。

> **证据锚点**：`已实现·证据有限`。事件协议见 README「SSE 事件协议」表；`planner/async_utils.py::watch_aiter` 每 0.5s 醒来检查 `cancel_event`，取消或超时都 `aclose` 生成器；`server.py` 用 `request.is_disconnected()` 置位。
>
> 测试：`evals/test_stream_plan.py::test_watch_aiter_timeout_closes`（超时必须 `aclose`）、`::test_watch_aiter_cancelled_stops_clean`、`::test_stream_plan_need_map_ignores_dispatch_timeout`。
>
> **说准边界**：服务端能区分的是 dispatch 超时（`timed_out`）、闸门降级（`degraded`）和异常（`error` 事件）。**取消是静默 `return`，客户端视角只是流结束**，没有 `cancelled` 事件。已发出的 MCP 请求和正在跑的 LLM 调用不会回滚，只是不再启动下一个。另外没有 HTTP 端点级测试（全仓无 `TestClient`），协议只靠前端解析和 mock 流验证。
>
> **两个测试自身的瑕疵**（如果面试官翻代码会看到）：①`evals/test_stream_plan.py` 里 mock 出的 `summary_delta` 事件类型，真实代码根本不产出（真实是 `token`）；②这些 mock 用例会**真的往 `workspace/results/` 和 `snapshots/` 写文件**，`conftest.py` 只把 `PLANS_DB` 和 `TRAVEL_MAP_FALLBACK` 重定向了。所以「跑单测不污染产物目录」不成立。

### 8. 改一版方案：快照与增量修订

在已完成的方案上提交「不要龙门石窟，改白马寺，路线顺一点」，让系统判断哪些要重跑、哪些能复用，并保证旧票务信息不串版本。

验收条件：

- 能区分三类修订：改变日期/地点/出行方式、只改行程内容、只改措辞。
- 只改行程时不再查票、不再抽槽位。
- 快照只接受合法 UUID，路径穿越要拒绝。
- 说清这套机制和「断点续跑」的区别。

> **证据锚点**：`已实现·有测试`（部分分支）。`planner/routing.py::classify_revision` 返回 `ticket_and_map` / `map_only` / `summary_only`；`pipeline.py` 修订分支读快照、合并槽位、用 `rewrite_plan_ids` 把旧 `plan_id` 的地图路径换成新的；`map_only` 复用旧 `ticket_context` 并标 `reused`，成文强制写「沿用上次查询」。
>
> 测试：`evals/test_stream_plan.py::test_map_only_revision_skips_extract_and_ticket`（断言 `extract_slots` 与 `get_ticket_agent` **都没被调用**）、`::test_plan_id_path_traversal_rejected`（`../../.env` 直接 error）、`evals/test_routing.py::test_classify_revision_four_factors`。
>
> **必须说准**：快照是**修订用的上一版上下文存档**，不是 checkpoint。全仓没有 `checkpointer` / `thread_id`，澄清的实际实现是「缺字段 → 发 `clarify` → **return 结束本轮** → 前端带 `slots` 重新 POST → 新 `plan_id` 重跑」。所以「中断恢复」这个说法不成立；能说的是「增量修订」。另外 `ticket_and_map` / `summary_only` 两条分支只有分类函数的单测，没有端到端测试；快照也没有 LRU（本地已积累 219 个 JSON，手动清理）。

### 9. 证明并行到底有没有并行

主提示词要求同一条消息里同时调度地图和车票。请设计一种方式证明它真的同时发生了，并给出「串行对照」。

验收条件：

- 不用单个布尔值当结论。
- 用开始时间差和墙钟构成可验证指标。
- 给出对照组，并说明对照组改了什么、没改什么。
- 结论受样本量限制时如实说明。

> **证据锚点**：`已实现·有测试`（指标）/ `证据有限`（结论）。`planner/dispatch.py` 记录 `map_active_at` / `ticket_active_at`，`pipeline.py` 输出 `map_ticket_active_delta_ms`、`dispatch_ms`、`map_ms + ticket_ms`。
>
> **为什么不能用 `parallel_dispatch`**：它还要求两个结果落在同一次工具消息里，而 ticket 约几十秒结束、map 要十几分钟，结果必然分两次回来，这个布尔值几乎恒为 false。`pipeline.py` 的 `timings.parallel_dispatch` 就是这样算的。
>
> 证据：`evals/serial.json`（每种模式各 5 次，每次新进程）、`EVALS.md`「并行对照」表。`FORCE_SERIAL=1` **只改提示词**，不保证模型照做（`evals/test_gate.py::test_force_serial_changes_rail_prompt` 也只断言提示词变了）。
>
> 讲结论时的口径：n=5、单场景，只能说「提示词能把开始时间拉开，但墙钟没省出一截」，不能说「并行没有收益」。

### 10. 设计一个可信的评测集

为槽位澄清、路由、工具故障降级和汇总闸门各写几条固定用例。把确定性测试与需要真实模型的质量评测分开。

验收条件：

- 记录样本数、模型、运行日期和关键配置。
- 不把小样本或同源模型打分说成普遍结论。
- 至少保留一个失败案例，并说明下一步如何定位。
- 说清跑批怎么做到可复现（进程隔离、超时、冷热分离）。

> **证据锚点**：`已实现·有测试`。黄金集 `evals/golden.json`（5 条真跑 + 5 条仅存 pytest node id 的离线项）；跑批 `evals/run_golden.py` 每个 attempt 新进程、带单次超时、`rows.jsonl` 逐行落盘、`split_cache` 冷热分开；判分 `evals/judge.py` 读快照里的工具原文对照。
>
> 测试：`evals/test_gate.py::test_golden_live_order_and_cache_split`、`::test_parse_judge_payload`。
>
> **本项目的自曝偏差**：judge 与被评模型是同一个网关模型，`judge_results.json` 里显式记 `same_model_bias: true`；分数只能当对照，不能当独立评审。已知失败案例是「地图上下文只剩 HTML 路径，成文仍写出景点/里程/票价区间」，根因是闸门不覆盖非车次事实——这条比拿 5 分更有面试价值。
>
> 引用任何评分前先看 `EVALS.md`「复核（2026-10-12）」：那一批数字跑在 `cda0fb1` 之前的旧流水线上，住宿地成为必答项后不能当基线。
>
> **还有三处口径要注意**：①`metrics.json` 里记的模型名是旧网关名，和代码里的模型常量对不上——报数字时要说明这是那次请求记下来的，不是当前配置；②「18 份」是打分份数，不是用例数，说成「测了 18 个用例」会被追问穿；③「至少保留一个失败案例」目前只存在于产物文件里，**没有测试强制它保留**，删了也不会挂。

### 11. 讨论从本地 Demo 到公网服务还缺什么

本项目当前按本地使用设计，并未部署到公网。请基于代码做一次假设性设计：如果将来开放给多用户，怎样处理用户输入、生成结果、快照、访问控制和删除请求？

验收条件：

- 明确区分「当前已实现」和「未来需要补充」。
- 检查结果文件的访问路径、鉴权范围、保留期限和清理方式。
- 给出部署前需要验证的边界，不把单进程限流或可选 API Key 描述成完整的生产安全方案。

> **证据锚点**：`已实现·证据有限`。已经有的：`POST /api/plan` 每分钟 8 次单进程内存限流、可选 `PLAN_API_KEY` 要求 `X-API-Key`（`server.py::_allow_plan` / `_reject_bad_api_key`）、`/results/` 静态挂载、规划历史 SQLite + `/api/plans`、`plan_id` 只收 UUID。
>
> 测试：`evals/test_gate.py::test_rate_limit_and_api_key`（函数级，非端点级）、`::test_plans_roundtrip_strips_tokens`、`::test_plans_db_failure_does_not_raise`、`::test_api_plans_registered_before_frontend`。
>
> **还没做、别含糊**：`/results/` 是**无鉴权静态目录**，知道文件名就能下；`/api/health` 也公开；快照和结果都**没有保留期限也没有清理任务**（README 明确写「不做自动 LRU」）；限流是单进程计数，多 worker 各一份，挡不住打到别的进程；没有删除接口；CORS 默认同源，但没有 CSRF、上传校验、用户隔离；快照里存着 `answer` 和 `slots`，且没有归属校验——知道 UUID 就能读。
>
> **一个真实的配置陷阱**：`frontend/app.js` 的 `fetch("/api/plan")` **不带 `X-API-Key`**。所以一旦设置 `PLAN_API_KEY`，网页端会直接 401，只有命令行/脚本能带头发请求。这是「可选 API Key」在 Web 入口上的实际代价，别把它讲成完整的访问控制。

每次复盘把每条能力归进下面四类，说不进任何一类的就是还没想清楚。**这份归类本身就是要交付的东西**，比逐条背验收条件值钱。分类原先是三类，「知缺陷」是我核对时补的——它比「证据有限」更糟：代码在，但行为和你嘴上说的不一样。

**A. 代码已实现且有测试**

- 软字段默认值（`apply_soft_defaults` 的填值本身有断言；`defaults_applied` 回传无断言）
- 规则路由 + 票务六态与优先级
- 成文闸门 + 重试一次 + 降级（`degraded` 文本自身也过闸门）

**B. 代码实现但证据有限**

- 「多日行程缺住宿地也弹卡」：只有 `EVALS.md` 一次端到端跑批，`clarify_missing` 无单测
- `defaults_applied` 回传：有实现，无断言

- 内容审核 400 重试层：逻辑有单测，真实 400 行为未验证

- 评测结论：judge 同源、样本小、旧数字已声明作废、模型名与当前配置不一致

**C. 知缺陷（实现有，但行为和题面/预期不一致，别当成已完成）**
