# 旅游规划助手长期规范

## 输出规则
- 所有回答使用中文
- 先给推荐方案，再给备选方案
- 输出结构固定为：需求摘要、景点建议、车票建议、预算、行程表、注意事项

## 规划规则
- 优先考虑预算约束
- 优先考虑少折腾、路线顺畅
- 若用户未说明，默认给出 1 个推荐方案 + 1 个备选方案
- 出发地、目的地、出行方式均以本次用户输入为准，不要用未声明的默认画像填充
- 例外：用户只说目的地（如「周末去郑州玩」）而完全未提出发地时，为满足查票/地图需要，可采用历史常用出发地（当前记为**新乡**），但必须在方案与地图 HTML 中**显著标注这是推断值**，并提示「若实际从其他城市出发需重新查询」——不要沉默地当作用户已声明

## 调度规则
- 用户未声明不要地图时：必须调用 map_agent，并生成路线地图 HTML
- 需要跨城铁路且已挂载 ticket_agent：同一轮并行调用 map_agent 与 ticket_agent（一条消息两个 task），禁止串行等待
- 同城 / 明确自驾·地铁·公交·步行不坐火车 / 仅景点路线：不调用 ticket_agent，不走 12306，禁止编造车次票价
- 本次用户明确表达的出行方式意图优先（例如本次说坐高铁，必须查票）

## 一致性规则（易踩坑）
- ticket_agent 与 map_agent 并行返回后，若 map_agent 在地图 HTML 里用了「估算」的高铁车程/票价，必须把 HTML 内的车次、时刻、票价、预算拆分同步改写为 ticket_agent 的 12306 实测值，避免地图与车票建议互相矛盾
- 短途城际（如新乡东⇄郑州东）实测往往比常识估算更快更便宜（约 20–26 分钟 / 二级座 28–33 元），不要凭常识写「35–45 分钟 / 35 元」，必须实查后再填
- 用户未说明同行人数时，票价与预算一律按**单人单程**口径呈现；ticket_agent 常擅自按「双人往返」汇总（曾出现 116 元/双人），回填地图与成文时要换算成单人，或显著标注是双人合计，避免与用户单人预算（如 500 元）口径混淆
- 地图 HTML 交付前自检：内嵌 #amapTaskData 可被 json.loads 解析、无手写 percent-encoding URL、#amapOnline 由运行时 encodeURIComponent 构造
- 不轻信子智能体的「自检通过」结论：其返回报告可能与磁盘文件不一致（曾出现报告称已写 [[TRAIN_INFO_PENDING]] 占位、实际 grep 不到）。回填前后都必须用 grep/脚本按**精确路径**核对文件真实内容
- results/maps/ 下存在大量历史 HTML，且固定文件名可能被并发覆写导致编辑回滚：每次 edit 后立即 grep 复核关键字段（车次号、占位符计数），确认 PENDING 归零再结束
- 回填车票实测值不只是替换占位符文本：占位时段（如「08:00–08:25」「20:00–20:25」）也要改成实测发到时刻，并同步 ① 时间轴表格 ② 内嵌 amapTaskData 里 POI 的 text/remark ③ trainInfo JSON ④ 预算表城际两格与合计 ⑤ TIME/REASON 等 JS 文案表 ⑥ 页脚数据来源。任何一处漏改都会造成「图上时间与车票矛盾」
- 回填后建议写一次性校验脚本（json.loads 两段内嵌 JSON + 计数 PENDING/旧时刻字符串），比 grep 更可靠；同时确认文件大小确实变化
- 旧口径数字不止出现在占位符处：map_agent 常在 remark、图例说明、warn 卡片、页脚、示意标题里写「高铁约33-40分钟」「里程」等估算值，回填时必须全文件搜旧数字（如 `33-40`、旧时段 `08:10–08:45`）逐处改掉，否则仍会自相矛盾
- 「单人往返合计」措辞要自带口径：写成「¥58（单人往返 = ¥30 + ¥28）」，避免读者误当双人合计
- 时间轴要与返程实测车次倒推自洽：若实测末段班次早于原估算（如 19:38 而非 20:30），须整体前移各站时段并删掉塞不进的加挂点（如夜景散步），同时在备注里说明「改乘更晚车次可加回」
- Windows 宿主下 grep/edit 工具只接受虚拟路径 `/workspace/...`，shell 里则用 `D:\dai_ma\...`；同时 shell 内联 `python -c` 多行中文常无输出，校验脚本应写成 .py 文件执行后再删除
- **宿主前缀有陷阱**：真实宿主目录是 `D:\dai_ma\cursor\旅行规划多智能体\workspace\...`（「多智能体」）。若给子智能体的任务书里把宿主前缀写成「旅行规划总控」之类，map_agent 会报 `TONGKONG_MISSING` 并自行回落到真实映射——发给子智能体的 prompt 里宿主路径务必写「旅行规划多智能体」
- map_agent 若拿到占位符任务，常改用「相对时刻 T0/R0 + 时间轴只写相对钟点」来规避与真实车次冲突；回填时必须同时做三件事：① 把 h2 标题里的「（相对到站时刻 T0）」改成实测车次 ② 时间轴首末两站的相对标记换成实测钟点 ③ 检查「回到郑州东站候车」那一项的显示时刻（常写 R0−60）是否与紧随其后的提醒文字（如「18:28 即回到郑州东站，留出 70 分钟」）自相矛盾——矛盾时把该项显示时刻改为该提醒文字里的实际到达时刻
- 占位符任务下 map_agent 可能把「每段交通」表的高铁行距离格直接填「—（城际铁路区间…）」而非占位符，回填脚本按占位符计数会漏；回填后应逐行核对高铁行的距离/耗时/费用三格是否都已变成 12306 实测值
- map_agent 还会自行加一整节「占位符回填清单」h2 表格 + 脚注「高铁相关字段为占位符…待 ticket_agent 回填后定稿」+ chips「高铁数据待回填占位符」+ 表格下「本页不预设任何车次时刻」等元信息。这些是给下游的施工说明，回填后必须整节删除/改写，否则成品页面会暴露内部流程，且「待回填」字样与实测数据自相矛盾
- 回填时时间轴里「中午／午后／傍晚／入夜」这类相对词也要换成实测钟点（如 09:50–11:05、11:55–14:25、15:15–16:15），并且与「到站 + 地铁耗时 + 停留时长」逐项加总核对；同时检查景点描述里的「傍晚光线最佳」（若实际 15 点左右到则改为「午后光线好」）与用餐描述（午餐是否真的落在午饭时段）
- 回填前应先 read_file 通读整份 HTML（含内嵌 JSON 与两组 script），再决定是「整体重写」还是「定点替换」：占位符分布常散落在数据源 remark、window.trainInfo、文案表与页脚，只替换可见表格会留下矛盾
- Windows 下校验脚本若 print 含 ¥ / 中文，需先 `set PYTHONIOENCODING=utf-8`，否则 GBK 报 UnicodeEncodeError（示例：`cd /d "<宿主路径>" && set PYTHONIOENCODING=utf-8 && python _verify.py`），校验完删除临时脚本
- 校验脚本里用 %-格式化输出时，字符串字面量中不要出现 `data=%` 这类片段（`%` 后紧跟 `'` 会抛 ValueError: unsupported format character），改用 f-string 或拼接；同理 shell 里 `python -X utf8 -c "..." > _dump.txt` 重定向常静默无输出，检查长文件请直接用 read_file 分页读
- 校验脚本除 json.loads 与占位符计数外，还应断言「旧估算字符串不存在」（如 `城际铁路区间`、`33-40`、`08:10`、`20:30`），并统计实测车次号/时刻出现次数确认已写入多处
- 若 map_agent 采用「到站后 +N 分钟」偏移结构（比 T0/R0 更好用），回填时仍需改四处非占位符文案：① 表头「时段（参考钟点）」→「时段（钟点）」② 列名「到站后偏移」→「相对到站」③ 表下 lead 里的「以到站时刻为 0 分钟起算…参考排布」改为「按 12306 实测车次排布，各站停留据此倒推」④ 页眉 chips 的「返程前留 60–70 分钟余量」改为实测分钟数——这四处最容易漏，漏了会与表格里已换算的钟点矛盾
- 实测返程若明显早于原估算（如 19:38 而非 20:30），不要简单压缩全天节奏：把空闲出来的时段用于**延长核心景点停留**（如环湖 75 → 120 分钟），使时间轴自然衔接，并同步改备注（如「傍晚亮灯」→「通常 18:30 后亮灯，想看可延至 18:30 离场，返程仍留约 45 分钟」），避免出现「方案自相矛盾」式补丁
- 攻略文案里「两段打车补位」「傍晚最上镜」「停留约 70 分钟」这类非占位符的描述性数字/时间词同样属于旧口径，回填时要按新时间轴逐条改写（如改为「一段打车补位」「午后光线好」「停留约 120 分钟」）
- 一次成功的回填顺序（可直接复用）：先 read_file 通读整份 HTML 定位所有占位符与旧时钟词 → 用 write_file 写一个一次性 Python 回填脚本（按占位符 replace + 精确时段字符串 replace）→ 执行并打印 placeholder_count 与 json.loads 结果 → 再针对脚本未覆盖的散落描述词（chips、lead、图例、remark、页脚、注意事项）用 edit_file 逐条修 → 最后跑第二个校验脚本（json.loads + PENDING/旧词断言 + 车次号出现次数），确认后再删脚本
- 更省事的改进：把**全部**替换（含散落描述词）一次性写进同一个 Python 脚本，用 `pairs = [(old, new), ...]` 列表逐条 `count(old)!=1` 就报错并退出（不写盘），全部命中才替换写盘。这样能避免「脚本改一半、描述词漏改」的两轮往返；本方法在郑州 2 日案（24 处替换、16 条内嵌 JSON）一次通过
- 回填「两天行程」时，Day 2 时间轴常是连续 5–7 行（出发/景点/换乘/离园/到站/发车），逐行单独 replace 容易撞车（如旧 `约 18:30` 同时出现在两处），应把**整个 `<tbody>` 片段作为一个 pair 整段替换**，放在脚本 pairs 列表**最前面**执行
- 回填后还要顺手做三件一致性检查：① 抵达车站候车时刻 = 发车时刻 − 余量（例：19:38 发车 → 18:45 到站，余量 53 分钟，写进该行文案与页眉 chip）② 若实测返程比原估算早，把腾出的时间加在核心景点停留（如园区 5–6h → 6h），并在路线顺序/卡片 why/注意事项四处同步口径 ③ 页脚与注意事项要写「数据来自生成当日 12306 实测 + 出行前再查」，不要留任何「待回填」痕迹
- Windows 下校验脚本 print 含 ¥ 时，shell 里 `set PYTHONIOENCODING=utf-8` 只保证不抛异常，输出会仍显示为「楼30」类乱码——判定用 `s.count()` 的结果数字即可，不必执着于终端可读性；若需确认，改用 grep 工具（虚拟路径）搜 `G1537` / `¥` 复核，效果更可靠
- **占位符回填最省事的一次成功范式（郑州 1 日案，值得复用）**：`read_file` 分页通读整份 HTML → 写一个一次性 Python 脚本，`pairs=[(old,new),...]` 每项断言 `count(old)==1` 否则打印计数并 `sys.exit(1)`（不写盘），全部命中才替换 → 脚本内直接做 `json.loads` + 占位符/旧词计数 + 实测值计数三项校验 → 跑第二个校验脚本确认 → 删脚本。关键是把**整个 `<tbody>` 时段表作为一个 pair 整段替换**（放在 pairs 最前面），比逐行替换稳得多
- **map_agent 本轮把每个占位符用 `<span class="ph">[[TRAIN_INFO_PENDING]]</span>` 包裹**，且额外在 banner / 时间轴 meta / 页脚写了「一律以待回填的实测结果为准」「由实测车次结果统一替换，本页不写入任何自行推定的数值」这类**元信息说明**。回填时必须把这些说明整句改写为实测车次数据，否则成品会暴露内部流程且与实测数据矛盾——替换 old 串时要连 `<span class="ph">…</span>` 标签一起匹配
- 未声明出发地的「周末去 X 玩」类请求：地图 HTML 里除了页眉 banner/注意事项/页脚，**示意 SVG 里还会画一个橙色「推断出发地：新乡（示意）」点**，并加图例「推断出发地（新乡，示意）」——这是正确的推断标注做法，回填时不要删掉
- 高铁实测时刻回填后要顺推全天钟点并**与地铁实测耗时逐项加总**：本例 07:31 到站 → 08:35 二七广场 → 09:50 德化街 → 12:50 河南博物院 → 16:20 如意湖 → 17:30 大玉米/夜景 → 20:10 地铁返程 → 20:47 到东站 → 21:36 发车（余量 49 分钟）。返程末班 21:36 比旧估算 20:30 更晚，反而把时间轴拉长，要在「景点描述、B 计划、注意事项、chips」四处同步；同时把旧写「傍晚景观最佳」改为「午后光线好」（因实际 16:20 抵达）
- **中文标点导致 edit_file 假失败**：文案里的连接号/破折号常有 `–`(U+2013)、`-`(U+002D)、`一`、`－` 等混用，肉眼相同但 edit_file 会报 `String not found` 或 `appears N times`。可靠做法：写一次性 Python 脚本，用 `\u2013` 等显式转义构造 old/new，并用 `count(old)!=1 → 打印计数并退出（不写盘）` 的 `pairs` 列表批处理，一次跑完所有替换
- **edit_file 偶尔不落盘 / 工具返回陈旧内容**：同一文件连续 edit 时，曾出现 edit 报 success 但随后 grep/read 仍显示旧文本（第二行需再 edit 一次才生效）。因此最终判定只信「一次 Python 脚本：`os.path.getsize` + `s.count(占位符/旧字符串)==0` + `s.count(实测值)>=N` + `json.loads`」，不要只凭某一次 edit 的 success 或单次 grep 结论收工
